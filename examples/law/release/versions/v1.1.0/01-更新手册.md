## 2. 本版本变更摘要（rhm 模板 §2）

### 2.1 新增功能

1. **组织结构统一真源（批次 3 P4-A）**：新建 4 张核心实体（`org_subject` / `org_unit` / `org_member` / `org_role_scope`）+ 4 张跨主体预留表；O01 9 大红线（isPrimary 原子化 / 策略 A 主键复用 / 8 层封顶 / 40017 办案组挂靠 / 数据权限唯一真源 / 单主体显隐 / ID 交集前置拦截 / 跨主体 4 场景矩阵 / denorm 两快照）全部落地。
2. **PHASE 三段灰度（P4-A → P4-B → P4-C）**：单开关 `OrgGraySwitchService.PHASE` 硬编码分步，禁止混包；P4-A 双写对账期失败仅 WARN（零回滚）；P4-B 切读兼容强一致（失败 500 回滚）；P4-C 断写清理旧写 410 Deprecated（不可逆，三方签字后执行）。
3. **110 分 Top5 分案推荐算法（批次 3 P3-14 O01-修05）**：组织匹配分 90（精确部门 50 / 子办案组 30 / 孙子级 10）+ 案件最少分 30（近 30 天未结最少归一化 20 + 近 14 天最少 10 + 高负载 ≥ 均值 + 2σ 扣 10 下限 0）+ 角色匹配分 30（首次指派 leader 30 / 历史组长 20 / vice 10 / member 0）+ 同分排序 3 键（lastAssignTime 最久 → org_member.createTime 最早 → userId 升序）；接口 `POST /case/admin/team/autoAssignCandidates` 返回 Top5，每条含 `{orgId,userId,score,orgScore,minCaseScore,roleScore,sortKey}` 6 个得分明细字段。
4. **案件中止 / 终止 / 恢复 S01 方案①（批次 4）**：中止 2 级审批 / 恢复 3 级审批 / 终止 4 级审批（最终关必须司法局管理员，缺则 40099）；中止可恢复仅 UPDATE 原案 stopEnd=1→0（不创建副本）；终止终态不可逆双层 40310（提交入口 + approveApply 内部兜底）；`fromStopEndService` 乐观锁 409 防并发篡改。
5. **独立中止终止恢复管理页（批次 4 S1-4）**：新增后台页 `/case/stop-end-manage`（前端 2 页 + 2 组件），11 列表字段（案件编号 / 办案组 / 执行人 / 投诉人 / 被投诉人 / 申请类型 / 申请状态 / 当前审批节点 / 当前审批人 / 申请时间 / 最后处理时间）+ 7 查询条件（案件编号 / 动作类型 / 审批状态 / 申请人 / 审批人 / 申请时间起 / 申请时间止）；详情页内嵌独立审批流程图 + 审核区 + 兜底指定审批人隐藏按钮（仅持 `case:stopEnd:emergencyAssignApprover` 权限可见）；后端 7 接口（分页 / 详情 / 审批链详情 / 流程步骤 / 跳转案件 / 兜底指定 / 9 行豁免审核信息查看）见 §3.2 与 03-config 脚本。
6. **方案② 6+2 类概念永久删除（批次 4 S01 §9.4）**：`newCaseId` / `sourceCaseId` / `case_relation` / `restoreRemark` / `relationType` / `resume_copy` / `restoredCaseId` / `parentCaseId` 在代码、SQL、字段层面永久清理；全文代码非注释命中门禁值 = 0；`record-archive` 与 `case_shared_relation` 语义合法字段改名为 `originCaseId` / `sharedRelationType` 避免门禁误判。

### 2.2 功能调整

1. **处分结构化真源强化（批次 2）**：处分 / 处罚结果统一以结构化结果表为业务真源；`case_info.isDisciplinaryAction` / `isPenalty` 仅保留为摘要字段双写。
2. **案件 / 惩戒导出标准化（批次 2）**：导出列头、字段映射、字典值统一口径；律师字典写前白名单校验。
3. **律所主体标识统一社会信用代码（批次 2）**：对外展示口径统一为"统一社会信用代码"，不再混用营业执照号；导入模板兼容旧列头。
4. **律所 `isLaw` 严格校验与导入兼容（批次 2）**：新增写入时强制校验 `isLaw=true` 必须满足律所主体条件；导入兼容旧数据。
5. **审计日志 9 字段口径（批次 1 兼容延续）**：关键业务接口审计日志必须包含结果状态、状态码、错误摘要、业务对象类型、业务对象 ID、请求标识等 6 核心字段，满足审计要求。
6. **9 行矩阵统一拦截机制（批次 4 S1-6）**：新增 `assertStopEndFlowMatrix` 统一断言，按 9 行×8 业务操作场景返回对应错误码：行 1=40311（主流程节点提交冻结）/ 行 2=40312（案件主表字段编辑冻结）/ 行 3=40313（资料上传冻结）/ 行 4=40314（讨论区冻结）/ 行 5=40315（律所端自查报告冻结）/ 行 6~8=40310（正常待办 / 超时统计 / 新申请冻结）/ 行 9=豁免（审批链自身 3 接口 stopEndApplySubmit / stopEndApplyHandle / stopEndManageReviewInfo 仍执行 40310 兜底，但不进入主流程矩阵 1~8 校验）；6 类 Service 事务首行统一接入；`getFlowTodos` 投影层额外黑名单过滤彻底屏蔽终止/中止案件正常流程待办。
7. **审批通过审计日志拆分为 6 条独立 INSERT（批次 4 S1-8，含空审批人兜底专用）**：`bizType=stop_end_approve`（审批节点动作）/ `stop_end_status_change`（stopEnd 变更前后）/ `stop_end_todo_close`（原正常待办批量关闭）/ `stop_end_msg_send`（站内信发送含接收人）/ `stop_end_flow_end`（申请流程结束合计耗时）/ `stop_end_empty_approver`（空审批人 50001 专用审计），6 条独立写，绝不合并为 1 条；`base_sys_log` 的 `BIZ_TYPE_ALLOWED` 枚举同步追加 6 项。
8. **审批链站内信 9 模板 + 工作台待办流转 + 近期日程同步（批次 4 S1-9）**：中止 / 终止 / 恢复 × 待审核 / 驳回 / 通过 = 9 组合站内信标题；终止通过站内信必附「本次终止不可逆，后续不得发起恢复申请」；中止通过附「案件已中止，可后续发起恢复申请」；恢复通过仅给申请人 + 执行人发「案件已恢复正常，请继续办理」；每关审批人生成对应类型工作台待办与近期日程（dueTime=当日 23:59:59，content 内嵌 `/case/list?id=xxx` 跳转），推进 / 驳回 / 终审时同步 todoFinish 关闭对应待办。
9. **denorm 两快照 4 触发点统一写入（批次 3 P3-9）**：`denormHandlerDepartmentId` / `denormGroupDepartmentId` 两个快照写入时机 = ① 首次分案 `assign()` + ② 承办人变更 `updateHandler()` + ③ 办案组变更 `updateGroupOrgId()` + ④ 详情读取时 NULL 自动回填（`info()` 接口首行），全部同事务写入；新增 `CaseDenormBackfillService` 可一次性批量回填所有历史 NULL 案件。
10. **client 端注销统一登录态治理（20260714-06 协作规则）**：logout 必须先调服务端注销接口，再清本地 token；所有受保护接口统一依赖服务端 token 校验，不允许前端自行推断。

### 2.3 缺陷修复

1. **旧组织结构表并发写 isPrimary 多主缺陷**：修复为 CASE WHEN 单语句原子化，并发 10 次恒 = 1 条主归属。「05-1 回归用例：MGMT-015」
2. **旧角色权限 JSON 数组与行式授权不一致缺陷**：统一以 `org_role_scope` 表为唯一真源，batchSaveByRole 先删后插幂等。「05-1 回归用例：STOP-022、STOP-025」
3. **终止案件可绕过申请入口直接变更 stopEnd 缺陷**：在 `approveApply` 内部新增双层 40310 兜底，原案 stopEnd=2 时任何审批再次触发都被截。「05-1 回归用例：STOP-032、STOP-034」
4. **方案②关键字 grep 误判缺陷**：`record-archive.service.ts` payload 中 `sourceCaseId` 改名为 `originCaseId`；`case_shared_relation.ts` 跨主体关系 `relationType` 改名 `sharedRelationType`；最终后端 0 / 前端 0 命中。「05-1 回归用例：TODO-005、MSG-006」
5. **旧 autoAssign 只有随机 0~13 无业务评分（批次 3 P3-14 缺陷修复）**：原简化版 `Math.floor(Math.random() * 13) + 1` 直接替换为 110 分 4 子项评分 + 同分排序 3 键 Top5 返回，完全符合 O01-修05 业务规则；补回原有 6 明细字段丢失问题。「05-1 回归用例：ASSIGN-002、ASSIGN-003、ASSIGN-010」
6. **终止态 stopEnd===2 前端仍可点「恢复申请」（批次 4 S1-11 缺陷修复）**：原 `canSubmitStopEndApply('resume')` 条件只判 `stopEnd !== 0`，没排除终止态 2 → 现在改成 `stopEnd !== 0 && stopEnd !== 2`，仅允许从 1=中止态发起恢复；40310 后端双层兜底仍保留，前端改只是体验优化。「05-1 回归用例：STOP-005、STOP-010、STOP-015」
7. **空审批人直接 500 崩溃无审计（批次 4 S1-5 缺陷修复）**：原 `pickApproverByStep` 返回 undefined 未做检查 → 现在封装 `assertApproverNotEmpty`，`approver.userId === 0` 立即抛 `CoolCommException('空审批人，请配置审批角色或兜底指定审批人', 50001)`；40099 语义统一修正为「空审批人/非法审批人/终态司法局管理员缺位」；同时写 1 条 `stop_end_empty_approver` 审计，可追溯是空审批人导致。「05-1 回归用例：STOP-035、PUNISH-002、LAW-007」

### 2.4 兼容性处理

1. **P4-A 零回滚承诺**：P4-A 双写阶段旧 6 张业务表读写完全兼容，双写新表失败仅打 WARN 日志不回滚主事务。
2. **P4-B 旧读兼容层**：读 100% 切新表，旧 Controller 返回结构不变，前端已有页面零改造；双写任一侧失败 = 500 回滚主事务（强一致）。
3. **P4-C 旧 JSON 历史展示**：`role.departmentIdList` 旧 JSON 仍可读展示但保存时被忽略，完全走 `org_role_scope` 真源。
4. **S01 旧接口兼容**：若前端调用旧版"立即中止/立即终止"（无审批链概念），自动降级为审批链第一关提交，向后兼容。
5. **tenantId 一期硬覆盖**：所有新表新 Service 的 add/update 事务首行无条件 `param.tenantId = 1`，前端传任何值均无效；后续多主体时再解锁。
6. **导入"统一社会信用代码"兼容旧列头**：导入模板同时兼容"营业执照号"与"统一社会信用代码"两种列头，避免历史模板立即失效。
