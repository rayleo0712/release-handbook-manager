## 1. 核心能力新增（业务面 · 对外发布口径）

### 1.1 处分结果标准化与导出规范

- **处分结果统一管理**：新增「处分结果」标准化登记能力，所有惩戒相关判断（是否启动、是否结案、工作台提醒、律所端上传限制、筛选查询、统计报表、结果导出）统一按标准化结果口径执行，避免历史多入口口径不一致
- **导出模板统一规范**：案件信息导出、处分结果导出两类模板的列标题、字段名称统一标准，解决历史不同版本模板列名混用导致的导入导出异常
- **律师白名单校验**：律师信息在批量导入、下拉选择、手工保存三个场景均强制校验白名单，从源头避免历史遗留脏数据进入业务流程
- **律所主体标识统一**：所有对外展示页面、操作文案、接口语义、导入导出场景统一使用「统一社会信用代码」作为律所唯一标识；导入模板同时兼容「营业执照号」「统一社会信用代码」两种历史列头，降低老用户切换成本

### 1.2 组织结构统一管理（第一阶段上线）

完成组织结构的统一重构，解决历史「部门、办案组、角色授权、用户归属」分散在多张表中的口径混乱问题：

- **主体与组织分层管理**：支持「律协/司法局等主体 → 部门/科室 → 办案组/项目组」多层级树状管理，层级最多支持 8 层
- **成员多组织归属**：一个用户可同时归属于多个组织（如既是民事部成员又是专项办案组成员），并可指定唯一主归属组织；支持「组长、副组长、成员」三种身份标注
- **角色数据权限精细化**：数据权限按「角色 × 组织范围」精确配置，替代历史「一张 JSON 数组写死」的粗粒度授权方式，支持后续按角色灵活扩展可见范围
- **平稳过渡三阶段**：本版上线为第一阶段（双写对账期），老用户操作习惯完全不变；后续两个阶段将依次切换读入口、清理历史冗余，全过程对业务无感

### 1.3 组织结构九大业务保障规则

为确保组织结构切换的业务连续性，本版内置九大保障规则（用户可能感知的规则列示如下）：

1. **主归属唯一性**：一个用户在同一主体下，主归属组织始终只有一个，避免统计报表重复计数
2. **历史编号无缝复用**：原有部门编号、办案组编号全部直接沿用，下游已出具文书中的历史编号不受影响
3. **层级与挂靠约束**：组织树最多 8 层封顶，避免无限嵌套；办案组必须挂靠在具体部门下，不能直接挂在主体根节点
4. **单主体自动简化界面**：如果当前系统只配置了一个主体，前端自动隐藏主体切换下拉，减少操作干扰
5. **ID 冲突提前拦截**：如果历史数据中存在部门编号与办案组编号重复的情况，升级脚本会提前拦截报错，避免迁移一半出现脏数据
6. **跨主体数据权限双维度**：支持「本主体全部数据」与「跨主体可见数据」两个独立权限维度，满足律协跨区协同、上级司法局观察下级等场景
7. **历史统计口径快照**：案件在承办人/办案组发生调整时，保留「当时所属部门」的时间点快照，历史统计报表不因后续人员调岗而前后对不上
8. **三阶段灰度开关**：组织结构切换分「双写对账 → 切读兼容 → 断写清理」三阶段，每阶段需签字确认后切换，禁止跳步
9. **异常兜底处理**：第一阶段双写期间，若新表写入出现异常，不影响老表的正常业务，问题记录在日志中后续人工对账即可

### 1.4 案件中止 / 终止 / 恢复全流程（分级审批上线）

严格按照「中止可恢复、终止不可逆、分级审批」的业务口径落地：

- **案件中止（两级审批）**：由办案组长发起 → 部门主任审批通过后，案件进入「中止办理」状态
- **案件恢复（三级审批）**：中止案件可发起恢复申请，由办案组长 → 部门主任 → 分管副会长逐级审批，通过后案件回到「正常办理」状态；恢复直接接续原案办理，不产生任何副本或重复案件
- **案件终止（四级审批 · 终态不可逆）**：需办案组长 → 部门主任 → 分管副会长 → 司法局管理员逐级审批，**司法局管理员为最终关**；审批通过后，案件进入「终止结案」终态，任何后续中止、恢复、再次终止申请均不再受理，确保案件结论严肃性

### 1.5 智能分案算法升级（加权评分 Top5 推荐）

- **替换历史随机分案**：将原有随机抽取 3 名候选人的分案方式，**全面替换为 110 分制加权评分算法**，返回评分排名前 5 的候选人并附带评分明细，解决「同部门长期苦乐不均、跨办案组指派不合理、分案靠运气」三大历史问题
- **分案理由透明可追溯**：每位推荐候选人均返回 6 项评分明细，指派界面可展示分案理由（如「组织匹配度高 + 近 30 天案件量最少 + 角色为历史组长」），分案审计时可回溯每一案的评分排名，杜绝人工暗箱操作
- **三项加权维度**：① 组织匹配分（承办人所在部门与案件部门越匹配得分越高）② 最少案件分（近 30 天/近 14 天案件量越少得分越高，对超平均值严重的承办人额外扣分）③ 角色匹配分（首次组长/历史组长/副组长/成员逐级降分）
- **历史统计口径保护**：分案指派完成后，自动保存承办人与办案组「当时所属部门」的快照，后续人员调岗不影响本案归属的历史统计

### 1.6 独立中止终止恢复管理页 + 九种状态统一展示

- **新增独立管理页面**：案件中止、终止、恢复三类申请从历史「案件详情内嵌操作」升级为「独立管理页面」，列表支持 11 个字段展示（案件编号、类型、当前状态、审批步骤、当前审批人、申请时间、原因摘要等）+ 7 个查询条件，操作效率大幅提升
- **审批流程图可视化**：详情页内置动态审批流程图，中止 2 关 / 恢复 3 关 / 终止 4 关，每关审批状态用颜色区分（灰色未到达、蓝色进行中、绿色已通过、红色已驳回），申请状态一目了然
- **兜底指定审批人**：针对审批人出差、离职等异常场景，拥有「兜底权限」的管理员可临时替换当前关的审批人，确保流程不卡壳；每次替换自动留痕，记录原审批人、新审批人、指定原因、操作人、操作时间五要素
- **九种组合状态统一标签**：中止 × 待审核/通过/驳回、终止 × 待审核/通过/驳回、恢复 × 待审核/通过/驳回，共九种组合状态用统一的标签颜色展示，解决历史状态颜色混乱、用户分不清的问题

## 2. 体验与安全优化（业务面 · 对外发布口径）

- **九类操作统一拦截保护**：案件一旦进入中止或终止状态，对主流程提交、案件信息编辑、终止资料上传、讨论区发布、律所端自查报告上传等九类操作统一拦截保护，避免用户在案件已休眠状态下误操作产生脏数据；审批链自身操作不受影响
- **审批动作逐条审计留痕**：审批通过动作按「审批结果、案件状态变更、待办关闭、站内信发送、流程结案」五环节拆分独立审计，外加「空审批人兜底」一条专用记录，审计穿透到每一环节，事后任何一条审批动作都可完整还原全链路上下文
- **九类站内信模板 + 工作台待办联动**：中止/终止/恢复 × 待审核/驳回/通过，共九种站内信标题模板，终止通过的站内信附带「不可逆」提示、中止通过附带「可恢复」提示、恢复通过仅通知承办人与申请人；每关审批人待办当日截止，点击可一键跳转到对应案件
- **历史案件统计口径自动补全**：对存量历史案件（本版上线前的案件），后台自动补全「承办人所属部门、办案组所属部门」两个快照字段，补全仅填历史空值、不覆盖已有数据；补全过程不影响前台查看，即使个别补全失败也不阻塞业务
- **历史重号自动清洗**：针对历史遗留的「部门编号与办案组编号重复」场景，升级脚本自动完成清洗，保留部门编号不变、仅重编号冲突的办案组，并同步修正所有引用处，用户无需手工处理
- **惩戒小组操作权限细化**：惩戒小组成员默认仅允许查看资料、受邀参与讨论、上传相关资料，不得编辑案件主表信息，避免越权操作
- **处分结果一致性校验**：对案件摘要标记与实际处分结果不匹配的场景（如摘要标记「未启动」却已有处分结果，或反之），系统立即阻断后续查看、编辑、归档等操作，强制用户先对齐口径，避免后续统计报表失真
- **终止态前端操作按钮适配**：终止结案的案件，前端不再显示「恢复」按钮，避免用户误触产生无效操作
- **审批并发冲突保护**：多人同时审批同一案件时，以发起申请时的快照状态为准，若审批通过前案件状态被其他流程篡改，系统立即提示并发冲突并驳回当前审批，确保状态一致性
- **客户端登录态统一**：历史「投诉人端、被投诉人端」两套登录态统一为一套，退出登录时清理干净不留痕，避免同一浏览器切换账号时串号
- **生产环境万能验证码拦截**：生产环境拦截「8888、9999、0000、1234」四类常见万能验证码，每次拦截均留痕审计，防止测试配置误上生产
- **字典导入白名单控制**：数据字典批量导入仅限 20 类默认登记字典，超出白名单的导入立即拦截并留痕，防止未知字典类型污染全局配置

## 4. 技术实现细节（技术面 · 内部专用，请勿外传）

### 4.1 组织结构双写与灰度切换机制

- **双写切面异常路由 `routeWriteFail`**：PHASE=A 双写失败仅 `logWarn` 不回滚主事务；PHASE=B/C 双写任一失败立即 `throw CoolCommException` 触发 500 回滚；已接入 14 处 catch
- **数据权限唯一真源写入**：`org_role_scope` 表 + 新缓存 `admin:orgScope:{roleId}`（TTL=6h），P4-B 期仅写新缓存；旧缓存 `admin:department:*` 只读不写（P4-A 期保留兼容读）
- **denorm 两快照防统计漂移**：`denormHandlerDepartmentId / denormGroupDepartmentId / groupOrgId` 三快照字段；同事务写 + 4 触发点写入（`assign() 指派 / updateHandler() 换承办人 / updateGroupOrgId() 换办案组 / info() 详情读时回填`）
- **denorm 回填服务双入口**：`CaseDenormBackfillService.backfillAllDenormSnapshot()`（100 条/批分页回填）+ `backfillDenormSnapshotByCaseId(id)`（单条回填）；回填「只填 NULL 不覆盖」，fallback 旧 `CaseTeamEntity.departmentId`；`info()` 回填段 try/catch 包裹不阻塞主流程
- **策略 A 冲突办案组 ID 自动清洗**（并入 `02-db-011`）：针对 `base_sys_department.id ∩ case_team.id` 重号场景，011 内置冲突自动清洗；保留部门 ID 与既有用户/角色授权不动，仅重编号冲突办案组 ID，同步修正 `case_info.groupId/groupOrgId` 等显式引用，随后同脚本内继续 P4-A 镜像迁移
- **PHASE 开关初始锁定**：`org_gray_switch.ts` 中 `readonly PHASE: 'A' | 'B' | 'C' = 'A'`，未签字情况下 B/C 禁止出现

### 4.2 S01 九行矩阵拦截与错误码体系

- **九行矩阵统一断言**：`CaseStopEndService.assertStopEndFlowMatrix()` 统一断言 9 行矩阵；行 2=40093 / 行 4=40094 / 行 6/7/8=40310 / 行 1/3/5 放行 / 行 9 审批链自身豁免
- **五款新增错误码 40311~40315**：各 ≥ 1 处实际调用（非注释）；40311=主流程提交拦截 / 40312=主表编辑拦截 / 40313=终止资料上传拦截 / 40314=讨论区发布拦截 / 40315=律所端自查报告拦截；与 `assertStopEndFlowMatrix` 行 1~5 一一对应

- **终止最终关 40099**：`approveApply` 终止 step=4 时 `approverRoles` 不包含 `JusticeAdmin` → 抛 40099；错误码 40099 命中 1 处，唯一使用场景
- **`fromStopEndService` 乐观锁 409**：提交申请时快照案件状态；审批通过前快照 != 当前 → 抛 409，错误消息包含「并发冲突：发起时快照 stopEnd=X，当前 stopEnd=Y」

### 4.3 审计 bizType 拆分与参数结构

- **6 个 stop_end_* 业务类型枚举独立声明**（`base/sys/log.ts`）：`STOP_END_APPROVE / STOP_END_STATUS_CHANGE / STOP_END_TODO_CLOSE / STOP_END_MSG_SEND / STOP_END_FLOW_END / STOP_END_EMPTY_APPROVER`，count=6
- **审批通过 5+1 条拆分写入**：`info.ts stopEndApplyHandle` 终审分支 5 条 INSERT + 空审批人 1 条 INSERT，合计 6 条 bizType 全命中；每条 params 携带独有业务上下文（审批链/状态前后/关闭的待办 ID 数组/接收人/耗时 durationText），不再合并为 1 条通用审计
- **空审批人 50001 独立兜底**：`pickApproverByStep()` 返回空审批人时 → `throw CoolCommException('当前步骤未配置审批人，请联系管理员配置', 50001)` 并写独立审计 `bizType=STOP_END_EMPTY_APPROVER`（含 step/caseId/actionType 3 字段）
- **审计日志 9 字段强约束**：结果状态 / 状态码 / 错误摘要 / 业务对象类型 / 业务对象 ID / 请求标识 + userId / action / ip；本轮 6 bizType 拆分严格按该口径落库
- **万能验证码生产拦截 bizType**：生产环境命中 8888/9999/0000/1234 → 先写 `bizType=LOGIN_UNIVERSAL_CODE_REJECT` → 再 throw 40309
- **字典导入白名单 bizType**：`dict import` 强制走 `predefinedTypeSet` 白名单（20 项默认登记字典），白名单外先写 `bizType=DICT_IMPORT_OUTSIDE_WHITELIST` → 再 throw 400

### 4.4 方案②关键字清理与向后兼容改名

- **8 类概念永久删除（代码非注释命中=0）**：`newCaseId / sourceCaseId / case_relation / restoreRemark / relationType / resume_copy / restoredCaseId / parentCaseId` 物理列、表、接口名、代码变量全部清理；CI/CD 可加正则门禁

- **方案② 6 类关键字 grep 门禁**：`\b(newCaseId|sourceCaseId|case_relation|restoreRemark|relationType|resume_copy|restoredCaseId|parentCaseId)\b` 后端非注释命中 0 条 + 前端非注释命中 0 条
