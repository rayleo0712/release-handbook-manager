# 发布自动化测试执行

本 Skill 专门负责“自动化测试执行”，用于把发布/UAT 测试从人工点击升级为可由 IDE 内置终端或等价命令行环境独立运行、可恢复、可落盘的自动化测试流程。

它与 `release-handbook-manager` 的边界如下：

- `release-handbook-manager` 负责发布材料真源、`05-1` 验收用例、账号准备、SQL/检查清单/日志等治理内容
- `release-test-auto` 负责读取这些真源，自动生成测试脚本并实际执行测试

## 别名约定

- 聊天中的简称统一为：`rta`
- `rta` 等同于 `release-test-auto`
- 当用户在对话中提到 `rta` 时，应按本 Skill 处理

## 何时使用

当用户出现以下意图时，应优先启用本 Skill：

- 要求 AI 模拟人工进行 UAT / 回归测试
- 要求基于 `05-1-功能验收用例(非技术版).md` 执行自动化测试
- 要求恢复数据库备份后再跑测试
- 要求在 IDE 内置终端或等价命令行环境中自动启动项目、修复 bug 后重启并续跑
- 要求生成自动化测试脚本、恢复脚本、恢复后校验脚本、测试结果报告

## 核心目标

本 Skill 的目标不是“在对话里手工点完测试”，而是要建立一条可独立运行的自动化测试链路：

1. 读取当前版本发布真源
2. 读取当前 `05-1` 中的账号与验收场景
3. 自动启动测试环境
4. 自动恢复数据库基线
5. 自动校验恢复结果
6. 自动执行正向 + 逆向自动化测试
7. 持续落盘进度与结果
8. 即使会话中断，也可以续跑到完成

## 一、输入真源

执行自动化测试时，输入真源固定如下：

### 1.1 版本真源

- `release/version.json`
- 读取：
  - `version`
  - `previousVersion`
  - 当前版本目录路径

### 1.2 验收真源

- 当前版本：`release/versions/{version}/05-1-功能验收用例(非技术版).md`

账号读取规则：

1. **优先读取当前版本 `05-1` 的 `## 2. 角色准备`**
2. 若当前版本某角色缺少 `测试账号` 或 `测试密码`，才允许读取上一个版本同名 `05-1`
3. 上一个版本路径固定为：`release/versions/{previousVersion}/05-1-功能验收用例(非技术版).md`
4. 禁止继续向更早历史版本追溯
5. 若 `previousVersion` 为空、缺失、不存在或当前已是首个版本，则不得再尝试历史迁移；此时只允许使用当前版本 `05-1` 已填写的账号信息与默认密码规则
6. 若进入**自动化执行模式**后，当前测试范围所需角色仍无法解析出 `测试账号`，则必须中止执行并明确列出缺失角色；密码允许按默认规则补足，但账号不能为空

### 1.2.1 逆向场景补齐辅助真源

当 `05-1` 中逆向场景不足、需要由 AI 自动补齐时，可读取以下辅助真源：

- 当前版本 `01-更新手册.md`
- 当前版本 `04-发布检查清单.md`
- 项目中的菜单 / 路由 / 权限配置
- 项目中的接口文档、状态流转说明、角色权限说明

约束：

1. 只有在上述辅助真源至少存在一类、且足以支撑页面 / 状态 / 权限判断时，才允许自动补齐逆向场景
2. 若缺少这些辅助真源，本 Skill 应明确提示“逆向测试真源不足”，不得凭空脑补逆向场景
3. 自动补齐的逆向场景必须在结果报告中单独标记为“AI 自动补充逆向场景”
4. 自动补齐的逆向场景必须生成稳定的 `case_id`，并纳入 `test-output/case-results/*`、`total_count`、`completed_count`、`checkpoints.json` 与最终报告统计；不得只在文字说明中提及而不进入统一计数

### 1.3 环境启动真源

自动化测试必须依赖“IDE 内置终端或等价命令行环境可直接执行的启动命令”。

要求项目提供**与本次测试范围相匹配**的启动命令。

若执行的是页面级 UAT / UI 回归 / 端到端流程回归，则至少满足以下之一：

- 一体化联调启动命令
- 测试模式启动命令
- 可分别启动前端与后端，且测试库 / 依赖服务已可用

仅有前端启动命令、或仅有后端启动命令，不足以宣称可以稳定完成整链路自动化测试。

常见可用类型如下：

- 前端启动命令
- 后端启动命令
- 一体化联调启动命令
- 测试模式启动命令

若项目没有标准启动命令，本 Skill 不应假设可稳定执行长时间自动化测试，应先提示用户补齐。

通用 IDE / 终端执行约束：

- 启动、重启、测试、恢复等操作应优先通过 IDE 内置终端命令或等价命令行环境完成，不应依赖人工点击 IDE 面板
- 若项目需要“修复 bug → 重启服务 → 继续回归”，则启动命令必须可重复执行，且应支持停止旧进程后重新启动
- 推荐为项目沉淀以下至少一个标准命令：
  - `npm run dev`
  - `npm run start:test`
  - `pnpm dev`
  - `docker compose up -d`
  - 或项目自定义 `scripts/test-auto/start-env.ps1`

### 1.4 自动化测试结果文件真源

自动化测试必须把状态持续写入磁盘，至少包含以下文件：

- `test-output/run-status.json`
- `test-output/checkpoints.json`
- `test-output/case-results/{case-id}.json`
- `test-output/final-report.md`

推荐字段：

**`run-status.json`**

```json
{
  "version": "v1.2.3",
  "status": "running",
  "total_count": 0,
  "completed_count": 0,
  "passed_count": 0,
  "failed_count": 0,
  "skipped_count": 0,
  "current_case_id": "",
  "started_at": "",
  "updated_at": "",
  "completed_at": ""
}
```

**`checkpoints.json`**

```json
{
  "last_completed_case_id": "",
  "completed_case_ids": [],
  "failed_case_ids": [],
  "resume_from_case_id": ""
}
```

### 1.5 数据基线真源

必须存在以下至少一类输入：

- 数据库备份文件路径
- 数据恢复脚本路径
- 基线数据导入命令

若三者都不存在，本 Skill 不得假装可以稳定完成自动化回归。

## 二、工作模式与执行前置条件

### 2.1 脚本生成模式

当用户意图是：

- 生成自动化测试脚本
- 生成恢复脚本 / 恢复后校验脚本
- 先搭建自动化测试骨架，暂不真正执行

则允许进入**脚本生成模式**。

约束：

1. 可在当前发布材料未完全齐备时先生成脚本骨架、模板文件、TODO 占位说明
2. 若缺少启动命令、测试账号、数据库基线等关键信息，必须明确标记“脚本已生成，但当前仍不可直接执行”
3. 不得把“已生成脚本”误报为“已具备稳定自动化执行条件”

### 2.2 自动化执行模式

当用户意图是：

- 直接执行 UAT / 回归 / 发布前自动化测试
- 恢复数据库后立即跑测试
- 修复 bug 后重启并续跑

则进入**自动化执行模式**，并且必须满足以下最小条件：

1. 使用环境支持 **IDE 内置终端或等价命令行环境**，且可独立执行启动命令
2. 项目具备与本次测试范围相匹配的启动命令；若执行 UI / UAT / 回归，则至少满足“一体化启动”或“前后端均可启动且测试库 / 依赖服务可用”
3. 存在可恢复的测试数据库基线
4. 当前版本 `05-1` 已存在并可读取
5. 当前测试范围涉及的角色，在“当前版本优先、上一个版本兜底”解析后，必须都能得到可用 `测试账号`；密码可按默认规则补足，但账号不能为空
6. 当前测试库允许自动恢复，不得指向生产库/准生产库

## 三、生成内容

本 Skill 在执行时，应尽量自动生成以下内容，而不是让执行人手工拼装：

### 3.1 启动脚本

用于在 IDE 内置终端或等价命令行环境中启动当前项目，例如：

- `scripts/test-auto/start-env.ps1`
- `scripts/test-auto/start-env.sh`

职责：

- 启动依赖服务
- 启动后端
- 启动前端
- 输出 PID / 端口 / 健康检查信息

### 3.2 数据恢复脚本

例如：

- `scripts/test-auto/restore-db.ps1`
- `scripts/test-auto/restore-db.sh`
- `scripts/test-auto/restore-db.sql`

职责：

- 读取备份文件
- 恢复到测试库
- 输出恢复日志

### 3.3 恢复后校验脚本

例如：

- `scripts/test-auto/check-db-after-restore.sql`

职责：

- 校验测试账号是否存在
- 校验关键角色是否存在
- 校验关键业务基线数据是否存在
- 输出 PASS / FAIL、成功数 / 失败数

### 3.4 自动化测试执行脚本

例如：

- `scripts/test-auto/run-uat-auto.ps1`
- `scripts/test-auto/run-uat-auto.sh`

职责：

- 读取 `05-1`
- 读取账号
- 登录系统
- 按用例顺序执行页面自动化 / 接口自动化
- 为 AI 自动补充的逆向场景生成稳定 `case_id`
- 每条结果立即落盘

### 3.5 测试结果文件

例如：

- `test-output/run-status.json`
- `test-output/checkpoints.json`
- `test-output/case-results/*.json`
- `test-output/screenshots/*`
- `test-output/final-report.md`

要求：

- 每条用例至少生成 1 份结构化结果
- AI 自动补充的逆向场景也必须按普通用例生成结构化结果，并进入统一计数
- 每次截图文件名应包含用例编号与时间戳
- `final-report.md` 必须引用 `run-status.json` 的最终统计值，不得人工目测拼写

## 四、测试覆盖规则

自动化测试**不得只覆盖正向场景**。

### 4.1 正向场景

- 主流程可顺利执行
- 多角色审批链可走通
- 列表查询、分页、详情展示正常

### 4.2 逆向场景

至少补齐以下三类：

1. **权限逆向**
   - 无权限账号访问页面
   - 无权限账号直接打开 URL
   - 非当前审批人尝试审批

2. **状态逆向**
   - 非法状态下重复提交
   - 已终止对象尝试恢复
   - 已处理记录再次操作

3. **输入逆向**
   - 必填项为空
   - 超长输入
   - 非法格式
   - 边界值输入

规则：

- 若 `05-1` 已明确写出逆向场景，则严格按 `05-1` 执行
- 若 `05-1` 主要只有正向场景，且 `01` / `04` / 菜单路由权限配置 / 接口文档等辅助真源充足，本 Skill 才可基于页面、状态、权限补齐必要逆向测试
- 若辅助真源不足，应明确提示“逆向测试真源不足”，不得凭空补齐
- 自动补齐的逆向测试必须在结果报告中单独标明“AI 自动补充逆向场景”

## 五、长时间运行与中断恢复

这是本 Skill 的强制能力，不能省略。

### 5.1 不依赖会话持续存活

自动化测试必须通过 **IDE 内置终端或等价命令行环境中的独立脚本或进程** 运行，不得依赖聊天会话持续不断线。

### 5.2 每条用例执行后立即落盘

每执行完 1 条测试用例，必须立刻写入结果文件，包括：

- 用例编号
- 角色
- 执行时间
- 通过/失败/跳过
- 截图路径
- 错误信息

### 5.3 断点恢复

必须支持续跑：

- 读取 `checkpoints.json`
- 跳过已完成用例
- 从未完成用例继续

若测试过程因以下原因中断：

- 聊天会话中断
- 终端命令被停止
- 服务重启
- AI 修复 bug 后需要重新启动项目

则应按以下顺序恢复：

1. 检查 `run-status.json` 是否仍为 `running`
2. 读取 `checkpoints.json`
3. 重新启动环境
4. 跳过已完成用例
5. 从 `resume_from_case_id` 或下一个未完成用例继续

### 5.4 完成判定

只有以下条件同时满足，才可判定“全部测试完成”：

1. `completed_count == total_count`
2. `passed_count + failed_count + skipped_count == completed_count`
3. `run-status.json.status == "completed"`
4. `completed_at` 已写入且非空
5. `final-report.md` 已生成

若缺任一项，均视为“测试未完成”，不得误报完成。

### 5.5 防卡死规则

- 单用例必须设置超时
- 页面等待必须设置超时
- 超时后要记录失败并继续后续用例
- 不得因 1 条用例挂死导致整批测试永远不结束

建议默认值：

- 页面加载等待超时：30 秒
- 单用例超时：180 秒
- 单角色登录超时：60 秒
- 恢复数据库超时：按项目大小单独设置，但必须写入脚本注释

### 5.6 修复后重启续跑

当 AI 在自动化测试中定位到 bug 并完成修复后：

1. 应优先停止旧测试进程与旧服务进程
2. 重新执行 IDE 内置终端或等价命令行环境中的启动命令
3. 重新执行健康检查
4. 判断是否需要恢复数据库基线
   - 若修复内容会影响测试数据一致性，则应重新恢复数据库
   - 若仅为页面展示或前端交互修复，可按需直接续跑
5. 使用续跑模式继续执行，而不是从头盲目全量重跑

## 六、执行顺序

本 Skill 执行时，应按以下顺序：

1. 读取 `release/version.json`
2. 读取当前版本 `05-1`
3. 补齐账号信息（当前版本优先，上一个版本兜底）
4. 检查启动命令是否存在
5. 生成或更新启动脚本
6. 生成或更新恢复脚本
7. 生成或更新恢复后校验脚本
8. 在 IDE 内置终端或等价命令行环境中启动测试环境
9. 恢复数据库基线
10. 执行恢复后校验
11. 生成或更新自动化测试执行脚本
12. 执行正向 + 逆向测试
13. 持续写入结果文件
14. 生成最终测试报告
15. 回填当前版本发布材料
    - `05-发布后验证记录.md`：回填技术执行结果、恢复校验、失败日志、脚本输出
    - `05-1-功能验收用例(非技术版).md`：回填用户可见结果、通过/不通过、截图路径、备注
    - `01-更新手册.md` 或 `05`：登记结构化结果文件、截图、日志路径，保证可追溯

补充：

- 若执行过程中发生代码修复，应在“第 8 步启动测试环境”与“第 9 步恢复数据库基线”之间插入“停止旧进程 → 重启环境 → 判断是否重置数据”的续跑流程

## 七、结果输出要求

最终必须至少输出以下信息：

1. 本次测试版本号
2. 执行环境与启动命令
3. 是否成功恢复数据库
4. 总用例数
5. 成功数
6. 失败数
7. 跳过数
8. 失败片段 / 失败用例清单
9. 截图与日志路径
10. 是否真正“全部完成”
11. 本次是否发生“修复后重启续跑”
12. 本次逆向场景中哪些是 `05-1` 原生提供，哪些是 AI 自动补充
13. `05` / `05-1` / `01` 是否已完成回填与归档

## 八、重要限制

- 不得连接生产库或准生产库自动恢复数据
- 不得把“环境没准备好”伪装成“测试通过”
- 不得只跑正向主流程就宣称完成自动化回归
- 不得把聊天会话存活当作测试完成保障
- 不得只输出日志而不写结构化结果文件
- 不得只生成 `test-output/*` 而不回填当前版本发布材料
- 不得忽略 `05-1` 当前版本账号真源
- 不得为了补账号信息继续扫描更早历史版本
- 不得在没有标准启动命令的前提下假装可以稳定自动化测试

## 九、推荐触发语句

以下表达应直接触发本 Skill：

- “请基于当前 05-1 自动跑一轮 UAT”
- “恢复测试基线后执行回归测试”
- “让 AI 模拟人工测试当前版本”
- “修完 bug 后重启并续跑自动化测试”
- “生成数据库恢复、校验和自动化测试脚本”
