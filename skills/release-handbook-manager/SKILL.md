# 版本发布手册管理

本 Skill 用于在项目内建立并维护一套可复用的版本发布治理机制，覆盖版本号管理、更新手册维护、数据库与配置脚本沉淀、发布检查、发布后验证、版本更新日志整理等工作。

## 适用前提

- 本 Skill 以“AI 深度参与开发过程”为主要适用前提
- 最适合 AI 持续参与需求分析、代码实现、改动整理和发布收口的协同开发场景
- 如果项目基本不用 AI 开发，或只在临近发版时少量使用 AI，不适合使用本 Skill
- 在低 AI 参与场景下，不得把本 Skill 表述为能够自动完整识别全部功能变化、所需 SQL、脚本与发布步骤

## 别名约定

- 聊天中的简称统一为：`rhm`
- `rhm` 等同于 `release-handbook-manager`
- 当用户在对话中提到 `rhm` 时，应按本 Skill 处理

当用户提出以下需求时，应优先启用本 Skill：

- 初始化项目的版本发布治理能力
- 在项目中创建版本配置文件
- 在项目中创建版本发布相关规则
- 为当前版本建立或补齐发布材料
- 在开发过程中持续登记当前版本的发布变更
- 整理当前版本的数据库脚本、配置脚本、人工操作步骤
- 在准备发布前检查版本材料是否完整
- 根据当前版本材料生成发布检查清单、发布后验证记录、版本更新日志

## 一、核心目标

本 Skill 不是只生成一份发布文档，而是要把以下机制真正落到项目内：

1. 项目内必须有唯一版本配置文件，作为当前版本号真源
2. 每个版本必须有唯一更新手册，作为当前版本发布内容真源
3. 凡是可通过数据库执行的变更，必须脚本化
4. 凡是不能脚本化但又必须执行的事项，必须登记为人工操作步骤
5. 发布时必须按版本手册逐步执行，而不是依赖口头说明或聊天记录
6. 版本更新日志应从当前版本更新手册中提炼生成

### 重要边界说明

- 本 Skill 不具备独立的“版本差异自动分析引擎”
- 本 Skill 不会凭空知道未留痕的功能变化、数据库变更、配置变化或人工操作项
- 只有在 AI 已持续参与开发过程、并掌握较完整上下文时，才更适合辅助生成 SQL、脚本、发布步骤和版本更新日志
- 当 AI 参与较少时，不适合使用本 Skill

## 二、版本号规则

### 2.1 唯一真源

- 当前版本号只能以 `release/version.json` 为唯一真源
- 禁止以 Git 提交记录、分支名、Tag 名等作为版本号唯一依据

### 2.2 格式约束

- 版本号格式固定为：`v主版本.次版本.修订号`
- 示例：
  - `v1.0.0`
  - `v1.3.2`
  - `v2.5.1`

### 2.3 维护原则

- 每次进入新的开发迭代或发布周期前，必须先维护 `release/version.json`
- 当前版本涉及的手册、脚本、发布检查、验证记录、更新日志，均必须归属于该版本号

### 2.4 版本号人工维护强制约束（一票否决红线）

**本条为一票否决级别的强制约束，违反即视为 Skill 执行失败：**

- `release/version.json` 中的 `version` 字段必须由人工明确指令触发维护，AI 不得在任何场景下自动生成或自动升级版本号，包括但不限于：
  - 开发环境代码变更后，AI 不得自动 bump 版本号
  - 新增功能、修复缺陷、调整配置后，AI 不得自行修改 `version` 字段
  - 初始化版本配置文件时，如无人工明确指定版本号，AI 只能使用占位模板（如 `vX.Y.Z` 或留空）并明确提示人工填写，不得擅自填入猜测的版本号
  - 维护阶段 AI 不得以任何形式的"智能版本建议"替代人工确认流程

- AI 仅允许在以下**两种**场景下操作 `version` 字段：
  1. 人工在对话中**明确给出具体目标版本号**并要求写入时，AI执行写操作
  2. 人工在对话中**明确指令版本号变更意图（如"把版本升级到 v1.2.3），AI 才可以执行写操作

- 除上述两种场景外，AI 发现版本号需要变更需求时，必须：
  - 立即停止自动写操作
  - 向用户明确提示："版本号必须人工维护，请给出明确指令后再执行"
  - 不得写入任何推测性的版本号变更

## 三、标准目录结构

首次初始化项目发布治理能力时，应创建如下结构：

```text
release/
  version.json
  versions/
    v1.0.0/
      01-更新手册.md
      02-db-001-数据库结构变更.sql
      02-db-002-历史数据修复.sql
      03-config-001-菜单权限配置.sql
      03-config-002-角色权限配置.sql
      04-发布检查清单.md
      05-发布后验证记录.md
      05-1-功能验收用例(非技术版).md
      06-版本更新日志.md
```

### 3.1 目录结构约束

- 当前版本目录统一为：`release/versions/{版本号}/`
- 当前版本目录采用单层平铺结构
- 禁止为 `02`、`03` 再建立多级子目录，避免执行发布时误操作
- **明确禁止**在 `versions/` 目录（含子目录）下存放任何 `YYYYMMDD-Windows-Terminal` 类临时命令文件、零散 PowerShell 脚本片段、临时命令笔记等；此类内容**必须合并写入** `01-更新手册.md §4.1.3 Windows PowerShell` 小节统一管理

### 3.2 文件编号含义（7类标准文件，05/05-1双轨配套缺一不可）

当前版本目录下标准文件共 7 类（编号：01/02/03/04/05/05-1/06），其中 `05` 与 `05-1` 为双轨配套文件，**缺一不可**，不得单独生成其中之一。

- `01-更新手册.md`：当前版本唯一真源，负责汇总发布材料（含脚本索引、人工操作、PowerShell命令、附件清单、签字区等）
- `02-db-xxx-说明.sql`：数据库类脚本（结构变更/历史数据修复等）
- `03-config-xxx-说明.sql`：配置类脚本（菜单/权限/角色/字典/参数等）
- `04-发布检查清单.md`：发布前检查材料（Checklist 真源）
- `05-发布后验证记录.md`：发布后技术验证真源（**仅限**测试/开发人员使用，覆盖 SQL 执行结果、代码自检、错误码校验、并发压测、缓存命中、denorm 回填、双写对账等全部技术维度验证）
- `05-1-功能验收用例(非技术版).md`：发布后非技术验收真源（面向产品经理/最终用户/UAT 验收人员，采用页面/操作/预期三段式，**不得出现任何技术术语**）；与 `05` 形成双轨：技术验证用 `05`，业务/UAT 验收用 `05-1`，两者互补、互不替代、必须同时生成
- `06-版本更新日志.md`：面向正式发布说明的版本日志（双面结构：对外业务面+对内技术面）

## 四、必须脚本化与允许人工操作的边界

### 4.1 必须脚本化

凡是本质上可以通过数据库执行完成的变更，必须提供可执行 SQL 脚本，不允许只写文字说明。

以下内容必须脚本化：

- 数据库表结构变更
- 字段新增、修改、删除
- 主键、外键、索引、约束调整
- 存储过程变更
- 触发器变更
- 历史数据修复、回填、迁移
- 菜单配置
- 菜单下权限配置
- 角色权限分配
- 其他可通过数据库增删改查直接完成的系统配置

补充原则：

- 菜单、权限、角色权限等虽然可在页面上人工配置，但其底层本质是数据库操作，因此必须归类为脚本化
- 不允许只写“请去页面手工配置菜单/权限”这类模糊说明
- 每个 `02-db-xxx.sql` / `03-config-xxx.sql` 文件在**文件头部**都必须预留统一固定说明区，至少包含以下 4 段，且顺序不得颠倒：
  - `【脚本用途】`
  - `【执行前置条件】`
  - `【预期结果】`
  - `【执行后快速核对】`
- `【预期结果】` 必须集中写在文件头部固定说明区，明确列出“执行完成后应该看到什么结果”；**禁止**把预期结果零散写在 SQL 中部、尾部或多段注释里，避免执行后人工翻找遗漏
- `【执行后快速核对】` 必须给出最少 1 条可直接复制执行的核对 SQL 或核对方法，方便执行完成后立即比对结果
- 每个 SQL 文件在**文件尾部**还必须追加独立固定区：`-- 【执行后校验SQL】`；该区域必须提供可直接执行的校验 SQL，校验结果应尽量返回明确数值、状态或差异计数，**禁止**只依赖执行日志中的 `Query OK`、影响行数提示或肉眼逐段翻看日志来判断是否成功
- 当脚本内容较多、步骤较多或包含多段 DDL/DML 时，`-- 【执行后校验SQL】` 必须按脚本内逻辑分段编号，例如 `-- 1. 校验字段是否存在`、`-- 2. 校验回填数量是否正确`、`-- 3. 校验脏数据是否清零`，确保执行后可逐项核对结果值
- 校验 SQL 的目标是“让执行人直接看结果值判断是否通过”，因此优先使用 `COUNT(*)`、`SUM(...)`、`CASE WHEN ... THEN 'PASS' ELSE 'FAIL' END`、差异集查询等可判定写法；禁止只写笼统注释而不提供可执行校验语句
- 对于**一个 SQL 文件包含多个执行片段**的场景，必须升级为“**分片段校验 + 汇总结果**”模式：每个片段执行完成后，立即执行该片段对应的校验 SQL，并把校验结果写入统一结果集；文件尾部再统一输出成功计数、失败计数、失败片段明细
- 多片段脚本**不得**只在文件尾部放一个笼统总查询，也不得只统计成功条数而不保留失败明细；至少必须同时输出：
  - 全量片段校验结果明细
  - `success_count`
  - `fail_count`
  - 失败片段清单
- 如数据库支持临时表，**优先**使用临时结果表（例如 `tmp_rhm_check_result`）收集每个片段的校验结果；如不支持临时表，也必须使用等价的可查询结果集方案，保证最终仍能输出“明细 + 汇总 + 失败项”

推荐头部模板：

```sql
/*
【脚本用途】
1. {本脚本解决什么问题}

【执行前置条件】
1. {执行前必须满足的条件}

【预期结果】
1. {执行成功后应看到的结果}
2. {需要重点核对的结果}

【执行后快速核对】
1. {核对SQL或核对步骤}
*/
```

推荐尾部模板：

```sql
-- 【执行后校验SQL】
-- 1. {校验项名称}
SELECT CASE WHEN COUNT(*) = 1 THEN 'PASS' ELSE 'FAIL' END AS check_result
FROM information_schema.COLUMNS
WHERE TABLE_SCHEMA = DATABASE()
  AND TABLE_NAME = '{表名}'
  AND COLUMN_NAME = '{字段名}';

-- 2. {校验项名称}
SELECT COUNT(*) AS abnormal_count
FROM {表名}
WHERE {应当不存在的数据条件};
```

多片段脚本推荐模板：

```sql
DROP TEMPORARY TABLE IF EXISTS tmp_rhm_check_result;
CREATE TEMPORARY TABLE tmp_rhm_check_result (
    id INT PRIMARY KEY AUTO_INCREMENT,
    check_name VARCHAR(200) NOT NULL,
    expected_desc VARCHAR(500) NOT NULL,
    actual_desc VARCHAR(500) NOT NULL,
    pass_flag TINYINT NOT NULL,
    check_time DATETIME NOT NULL DEFAULT CURRENT_TIMESTAMP
);

-- 片段1：执行 SQL
-- {片段1执行语句}

-- 片段1：执行后校验并写入结果
INSERT INTO tmp_rhm_check_result (check_name, expected_desc, actual_desc, pass_flag)
SELECT
    '片段1-{校验项名称}',
    '{预期结果说明}',
    CONCAT('{实际结果前缀}=', COUNT(*)),
    CASE WHEN {通过条件} THEN 1 ELSE 0 END;

-- 片段2：执行 SQL
-- {片段2执行语句}

-- 片段2：执行后校验并写入结果
INSERT INTO tmp_rhm_check_result (check_name, expected_desc, actual_desc, pass_flag)
SELECT
    '片段2-{校验项名称}',
    '{预期结果说明}',
    CONCAT('{实际结果前缀}=', COUNT(*)),
    CASE WHEN {通过条件} THEN 1 ELSE 0 END;

-- 【执行后校验SQL】
-- 1. 查看全部片段校验结果
SELECT
    id,
    check_name,
    expected_desc,
    actual_desc,
    CASE WHEN pass_flag = 1 THEN 'PASS' ELSE 'FAIL' END AS check_result,
    check_time
FROM tmp_rhm_check_result
ORDER BY id;

-- 2. 查看汇总结果
SELECT
    COUNT(*) AS total_count,
    SUM(CASE WHEN pass_flag = 1 THEN 1 ELSE 0 END) AS success_count,
    SUM(CASE WHEN pass_flag = 0 THEN 1 ELSE 0 END) AS fail_count
FROM tmp_rhm_check_result;

-- 3. 仅查看失败片段
SELECT
    id,
    check_name,
    expected_desc,
    actual_desc
FROM tmp_rhm_check_result
WHERE pass_flag = 0
ORDER BY id;
```

### 4.2 允许人工操作

仅以下场景允许保留为人工操作步骤：

- 修改已有配置文件的内容调整（不含新增配置文件）
- 生产环境配置类操作
- 确实无法脚本化的事项

凡归类为人工操作的事项，必须明确登记：

- 操作入口
- 操作顺序
- 操作内容
- 目标结果
- 校验方式

禁止使用以下模糊表述：

- “现场处理”
- “按实际情况调整”
- “发布时再看”

## 五、首次初始化时必须创建的内容

当项目尚未具备这套机制时，本 Skill 应优先初始化以下内容。

### 5.1 版本配置文件

路径：

```text
release/version.json
```

推荐模板：

```json
{
  "version": "v1.0.0",
  "previousVersion": "",
  "releaseDate": "",
  "status": "developing",
  "owner": "",
  "description": "",
  "releaseGate": {
    "checklist04AllPassed": false,
    "uat051Conclusion": "pending",
    "phase3SignOff": {
      "dev": false,
      "test": false,
      "ops": false
    },
    "materialsSha256": ""
  }
}
```

字段说明：

- `version`：当前版本号
- `previousVersion`：上一版本号
- `releaseDate`：正式发布日期，未发布可为空
- `status`：固定为 `developing` / `released`；**AI 不得自动修改此字段，必须严格遵守 §8.5 门禁门槛**
- `owner`：当前版本负责人（仅 owner 本人有权限发人工指令触发 status → released）
- `description`：当前版本一句话说明
- `releaseGate`：**版本门禁字段（顶层对象，AI 不得自动置为通过）**，四个子字段含义见 §8.5：
  - `releaseGate.checklist04AllPassed`：`04-发布检查清单.md` 全部 Checklist 项是否已人工核验通过（布尔值 true/false）
  - `releaseGate.uat051Conclusion`：`05-1` UAT 验收结论，枚举值：`pending`（待验收）/ `passed`（全部通过）/ `partial`（部分通过）/ `failed`（不通过）
  - `releaseGate.phase3SignOff`：签字门禁对象；其下各布尔子字段由项目按实际签字步骤定义（如 `dev/test/ops` 或 `p4aToP4bSigned/p4bToP4cSigned/finalPhysicalDropSigned`），**仅当所有子字段均为 `true` 时才视为通过**
  - `releaseGate.materialsSha256`：核心发布材料校验值；用于校验 `01/04/05/05-1/06` 等关键材料是否与待发布版本一致，默认空字符串，未人工回填前不得视为通过

### 5.2 项目内规则文件

应在项目规则目录中创建一份“版本发布与更新手册规则”文件，用于长期约束项目协作。

推荐位置：

```text
.trae/rules/YYYYMMDD-08-协作-版本发布与更新手册规则.md
```

规则文件应至少覆盖以下内容：

- 版本号唯一真源规则
- 版本材料目录规则
- 更新手册唯一真源规则
- 强制登记范围规则
- 必须脚本化规则
- 允许人工操作规则
- 发布执行规则
- 更新日志沉淀规则
- 发布材料完整性规则
- 维护责任规则

### 5.3 当前版本目录

应根据 `release/version.json` 中的版本号创建当前版本目录：

```text
release/versions/{版本号}/
```

### 5.4 当前版本模板文件清单（必须同时生成 05/05-1 双轨模板）

应在当前版本目录下**强制同时补齐以下 5 个模板文件**（其中 05/05-1 必须成对生成，缺一不可）：

- `01-更新手册.md`
- `04-发布检查清单.md`
- `05-发布后验证记录.md`
- `05-1-功能验收用例(非技术版).md`
- `06-版本更新日志.md`

必要时根据当前版本需求创建：

- `02-db-001-xxx.sql`
- `03-config-001-xxx.sql`

**初始化阶段强制约束（关于 05-1）：**

- `05-1` 模板中 §八「验收汇总表」的 P0/P1/P2 计数行（含合计数字）**必须全部留空，不得预填任何数字**；数字回填操作必须在验收启动前，按 §6.3.1(f) 约定的两条 PowerShell 命令人工执行回填

## 六、更新手册与配套模板

### 6.1 `01-更新手册.md`

职责：

- 作为当前版本唯一真源
- 记录本版本全部变更事项
- 编排发布执行顺序
- 记录脚本、人工操作、回滚方案、附件清单

推荐结构（严格遵循，9 章节固定，禁止自行增加其它章节导致内容臃肿）：

```md
# {版本号} 更新手册

> 版本真源：release/version.json — 当前 {版本号} / 上一版 {上一版本号}
> ⚠️ 严格串行：SQL 按编号顺序执行，禁止跳步；灰度按开关分步；版本号必须人工维护，AI 不得自动修改。
```

**(a) 变更台账（唯一真源，强制）：**

- `01-更新手册.md` 中必须新增 `### 3.7 变更台账（唯一真源）` 小节，作为当前版本功能变更的唯一追踪真源
- 每个功能变更在当前版本中只能保留 **1 条主记录**，不得为同一业务目标拆出多条重复主记录
- 当开发过程中发生功能补充、规则调整、交互变更、入口变更、登录方式扩展等线性延续变化时，必须沿用原 `变更编号` 持续维护，不得新开平级主记录
- `当前有效摘要` 是发布说明、测试设计、验收回归的唯一口径；若后续发生变更，必须同步更新 `当前有效摘要`
- `原始需求摘要`、`当前有效摘要`、`本轮调整摘要` 三者必须同时保留，禁止仅保留局部调整描述导致整体功能目标丢失
- 已废弃的功能不得直接删除，应将 `当前状态` 改为 `cancelled`
- 已并入其他主变更的记录不得重复维护，应将 `当前状态` 改为 `merged`，并在 `备注` 中注明并入目标编号

**推荐表头（固定顺序）：**

```md
| 变更编号 | 所属版本 | 功能域 | 当前状态 | 原始需求摘要 | 当前有效摘要 | 本轮调整摘要 | 影响范围 | 关联用例编号 | 备注 |
|---|---|---|---|---|---|---|---|---|---|
| CHG-REG-001 | v1.2.3 | 注册登录 | testing | {原始业务目标} | {当前最终生效口径} | {本轮相对上一轮的调整} | {页面/角色/流程/数据} | UAT-REG-001,UAT-REG-002 | {可选补充说明} |
```

**字段约束：**

- `变更编号`：当前版本内唯一，推荐格式 `CHG-{模块缩写}-{三位序号}`，如 `CHG-REG-001`
- `所属版本`：填写当前版本号
- `功能域`：填写用户可理解的业务域名称，不得使用内部开发代号
- `当前状态`：必须从以下枚举中选择：`draft / developing / adjusting / testing / released / cancelled / merged`
- `原始需求摘要`：填写该功能第一次提出时的完整业务目标
- `当前有效摘要`：填写当前最终生效、用于发布说明和验收设计的唯一描述
- `本轮调整摘要`：填写本轮相对上一轮发生的变化；若本轮无变化可写 `-`
- `影响范围`：填写受影响的页面、角色、流程、数据范围
- `关联用例编号`：填写 05-1 中对应的用例编号集合

**状态联动规则（强制）：**

1. 若某条变更的 `当前有效摘要` 发生变化，则该条记录不得继续保持 `released`，应先调整为 `adjusting` 或 `testing`
2. 当 `release/version.json.status = released` 时，当前版本下所有非 `cancelled`、非 `merged` 的变更记录，其 `当前状态` 必须为 `released`，否则视为发布材料不一致
3. 若后续变化已经构成新的独立业务目标，且不再属于原功能线性延续时，才允许新增新的 `变更编号`

**(b) 01-更新手册精简原则（一票否决红线，违反即视为 01 内容不合规，打回重写）：**

4. 追加或创建对应脚本与更新手册内容
   - 所有内容均归属到已读取的当前版本号下，不得因内容增加而擅自切换或升级版本号
   - 如创建或补写 `02-db-xxx.sql` / `03-config-xxx.sql`，必须先在文件头部补齐 §4.1 规定的固定说明区，尤其是 `【预期结果】` 与 `【执行后快速核对】`，不得省略
   - SQL 文件写完后，必须在文件尾部补齐 `-- 【执行后校验SQL】` 固定区；当脚本包含多段逻辑时，校验 SQL 也必须按逻辑分段编号，保证执行人不依赖肉眼翻日志即可判断结果
   - 若 SQL 文件包含多个执行片段，必须为每个片段就近补一段校验写入逻辑，并在尾部输出“全部片段明细 + success_count + fail_count + 失败片段清单”；不得只保留总计数而缺失失败明细
5. 同步补充发布检查清单、发布后验证记录（技术版 05）、功能验收用例（非技术版 05-1）、版本更新日志所需内容
   - **05/05-1 双轨必须同时生成**：不得单独只生成 05 或只生成 05-1，任一缺失即视为维护步骤未完成
   - **05-1 的生成口径**：必须严格按 §6.3.1 规范，从 01 §2.1/§2.2 提取用户可感知功能、从 01 §2.3 提取缺陷修复转回归用例、排除 §6.3.1 明确禁止的所有技术术语
   - **05-1 角色准备区账号迁移（强制）**：生成 05-1 时，必须先读取 `previousVersion`，仅检查上一个版本同名 `05-1` 文件中的 `## 2. 角色准备`；若存在同名角色的 `测试账号/测试密码`，则优先迁移到当前版本，找不到时再回落模板默认值；严禁继续追溯更早历史版本
   - **05-1 用例编号反写交叉索引（强制）**：同步生成 05-1 时，若用户在 `01-更新手册.md §2.3 缺陷修复` 中写了 N 条缺陷修复记录（N≥1），则**必须**：
     1. 为每条用户可感知的缺陷修复在 05-1 中生成对应的回归验收用例，并分配唯一 05-1 用例编号（如 `BUG-001`、`ORG-FIX-003` 等）
     2. 将生成的「05-1 用例编号」**反写到 01 §2.3 对应缺陷修复条目的**每行末尾**，形成双向交叉索引；格式示例：
        - 01 §2.3 行原内容末尾追加：` 【05-1回归用例：BUG-007】`
        - 05-1 用例的「用例编号」列填写：`BUG-007`，并在「操作/预期」列对应描述该缺陷修复前的原始触发场景与修复后预期结果
     3. 01 §2.3 中纯后台、用户不可感知的缺陷修复（如纯 SQL 性能优化、死锁修复、缓存命中率优化等）不需要进入 05-1，但也必须在行末标注：` 【纯后台修复·不进入05-1】` 以便巡检时区分
   - 如维护过程中判断本次改动可能需要切分版本或升级版本号，必须向用户明确提示建议，等待人工明确指令后再执行版本号变更操作

### 7.3 发布前巡检阶段（核验项升级）

1. 检查版本号与目录是否一致
2. 检查脚本编号是否连续、用途是否清晰
   - 同时检查每个 SQL 脚本文件头部是否存在 §4.1 规定的固定说明区：`【脚本用途】/【执行前置条件】/【预期结果】/【执行后快速核对】`
   - 同时检查每个 SQL 脚本文件尾部是否存在 `-- 【执行后校验SQL】` 固定区，且校验语句能够返回明确结果值、差异数或 PASS/FAIL 判定
   - 如脚本存在多个执行片段，同时检查是否已按片段落校验结果，并在尾部输出 success_count、fail_count 和失败片段清单；缺任一项即视为不合规
3. 检查更新手册是否记录全部变更
4. 检查人工操作是否具备明确步骤与校验方式
5. 检查发布后验证（技术版 05）与回滚方案是否完整
6. 检查功能验收用例（非技术版 05-1）是否完整（由原 5 项扩展为 11 项核验）：
   - (1) 功能覆盖检查：是否已生成 `05-1-功能验收用例(非技术版).md`，且包含 01 §2.1/§2.2 全部用户可感知的新增与调整功能
   - (2) 回归覆盖检查：是否包含 01 §2.3 全部用户可感知缺陷修复的回归用例，且 01 §2.3 每条行末已反写对应 05-1 用例编号（交叉索引校验）
   - (3) 术语合规检查：是否已排除 §6.3.1 明确禁止的所有技术术语与纯后台验证项（SQL/错误码/字段名/缓存键/代码路径 等零出现）
   - (4) 10 列结构检查：所有用例表格是否严格采用 §6.3.1(f) 约定的 10 列固定列名与顺序（表头行逐字比对：`用例编号 | 来源变更编号 | 覆盖类型 | 优先级(P0/P1/P2) | 页面(中文路径+URL) | 操作(步骤编号123) | 预期(可判定结果) | 实际结果 | 验收人 | 备注`）；列名、列数、列顺序任一偏差视为不合规
   - (5) **变更映射检查（新增）**：05-1 中每条用例是否均填写合法的 `来源变更编号`，且该编号能够在 `01 §2.6 变更台账（唯一真源）` 中找到
   - (6) **变更漂移检查（新增）**：是否存在 `01 §2.6` 中 `当前有效摘要` 已更新，但 05-1 仍沿用旧测试点、旧步骤、旧预期的情况
   - (7) **覆盖类型完整性检查（新增）**：对重要业务变更，是否仍只保留 `主流程` 用例而缺少必要的 `逆向 / 异常 / 边界 / 回归 / 权限 / 状态流转` 覆盖
   - (8) **附件登记核验（新增）**：01-更新手册.md §12「附件清单」中是否已登记 ATT-04-1 条目指向 05-1：`ATT-04-1：05-1-功能验收用例(非技术版).md —— UAT验收用例真源`；未登记视为 01 不合规
   - (9) **签字区核验（新增）**：01-更新手册.md §13「签字区」中是否已存在 05-1 UAT 签字量化三行栏（缺一不可）：
     - `UAT 验收通过（P0 全过 + P1 通过率 ≥ 95%）：签字________ 日期________`
     - `UAT 验收结论摘要（不通过项清单索引）：签字________ 日期________`
     - `05/05-1 双轨结论一致确认：签字________ 日期________`
   - (10) **汇总表留空核验（新增）**：05-1 §八「验收汇总表」中 P0/P1/P2 计数（含合计行）在验收启动前**是否保持留空状态**；如已预填任何数字（即使是正确数字）也**直接判定不合规**，必须清除后置位空值，由两条 PowerShell 命令在验收前回填
   - (11) **双轨说明核验（新增）**：05-1 文档首部是否存在「双轨覆盖关系说明 4 条」完整文字（逐字比对 §6.3.1 建议首部结构中的 4 条说明）；缺失任一条即视为不合规

## 八、操作判断原则

### 8.1 何时应直接初始化

以下情况优先执行初始化：

- 项目内还没有 `release/version.json`
- 项目内还没有版本发布相关规则文件
- 用户明确要求建立版本发布治理机制
- 用户明确要求创建版本更新手册体系

### 8.2 何时应进入维护模式

以下情况优先进入维护模式：

- 项目中已存在版本配置文件与版本目录
- 用户要求补登记当前版本的变更事项
- 用户要求为当前改动补 SQL 脚本、发布清单、更新日志

### 8.3 何时应进入巡检模式

以下情况优先进入巡检模式：

- 用户要求准备发版
- 用户要求检查某个版本材料是否完整
- 用户要求核对当前版本是否缺少脚本、手册或验证记录

---

### 8.4 一票否决级 · 版本号人工维护 4 条红线（原文保留）

**本条为一票否决级别的强制约束，违反即视为 Skill 执行失败：**

1. `release/version.json` 中的 `version` 字段必须由人工明确指令触发维护，AI 不得在任何场景下自动生成或自动升级版本号（开发环境变更后不得自动 bump、功能/缺陷/配置调整后不得自行修改、初始化无人工指令时只能用占位模板、不得以任何"智能版本建议"替代人工确认）。
2. AI 仅允许在以下**两种**场景下操作 `version` 字段：① 人工明确给出具体目标版本号并要求写入；② 人工明确指令版本号变更意图（如"把版本升级到 v1.2.3"）。
3. 除上述两种场景外，AI 发现版本号需要变更需求时，必须立即停止自动写操作，向用户明确提示："版本号必须人工维护，请给出明确指令后再执行"，不得写入任何推测性变更。
4. 初始化创建版本配置文件时，如无人工明确指出版本号，不得擅自填入具体版本号，必须使用占位值（`vX.Y.Z` 或空字符串）并提示人工维护。

---

### 8.5 一票否决级 · 版本门禁字段（releaseGate 门槛规则）

> **前置依赖**：`release/version.json` 顶层必须存在 `releaseGate` 对象，至少包含以下四个字段（详见 §5.1 模板）；门禁字段满足要求 + 人工 owner 指令 = AI 方可操作 `status` 字段，否则一律禁止。

**门禁字段定义（4 个，缺一不可）：**

| 字段路径 | 类型 | 通过门槛值 | 含义 |
|---|---|---|---|
| `releaseGate.checklist04AllPassed` | `boolean` | **`true`** | `04-发布检查清单.md` 全部 Checklist 条目已由人工逐项核验签字通过；`false` = 仍有未通过项 |
| `releaseGate.uat051Conclusion` | `string`（枚举） | **`"passed"`** | `05-1` 验收结论：`pending`=待验收 / `passed`=**全部通过（门槛值）** / `partial`=部分通过 / `failed`=不通过；仅 `passed` 视为达标 |
| `releaseGate.phase3SignOff` | `object` | **对象下全部布尔子字段 = `true`** | 项目级签字门禁对象；可按项目定义为 `dev/test/ops`，也可定义为 `p4aToP4bSigned/p4bToP4cSigned/finalPhysicalDropSigned`；仅当对象下全部布尔子字段均为 `true` 时视为通过 |
| `releaseGate.materialsSha256` | `string` | **非空，且与待发布材料校验值一致** | 核心发布材料校验值；空字符串或校验不一致均视为未通过 |

**status 变更强制规则（违反视为 Skill 执行失败）：**

1. **允许 AI 执行 `status: "developing" → "released"` 的唯一组合条件（必须 100% 同时满足）：**
   - ✅ `releaseGate.checklist04AllPassed === true`
   - ✅ `releaseGate.uat051Conclusion === "passed"`
   - ✅ `releaseGate.phase3SignOff` 对象下全部布尔子字段均为 `true`
   - ✅ `releaseGate.materialsSha256` 非空，且已由人工确认与待发布材料校验值一致
   - ✅ 当前对话中，`release/version.json` 中的 `owner` 字段对应本人（即版本负责人）**在对话中明确发出人工指令**，例如："请把 v1.2.3 状态改为 released" / "v1.2.3 正式发布，更新 status"
   - 以上五项**有任意一项未达标，AI 必须立即停止写操作**，逐条向用户输出未通过的门禁字段及原因，不得修改 `status`。

2. **禁止任何场景下的自动 status 变更：**
   - AI 不得因巡检通过、脚本齐全、用例通过等任何自动判断结果，主动或自动修改 `status`
   - 非 owner（即对话人 ≠ `owner` 字段登记的负责人）发指令要求改 status 时，AI 必须明确拒绝："本版本号门禁仅允许 owner 本人发人工指令触发 status → released，请联系版本负责人 {owner} 本人操作"
   - 反向变更 `status: "released" → "developing"`（撤回发布）同样需要 owner 本人明确人工指令，AI 不得自动回退

3. **初始化/维护阶段 releaseGate 默认值约束：**
   - 初始化生成 `version.json` 时，`releaseGate` 字段**必须固定写入门槛否定值**：`checklist04AllPassed: false`、`uat051Conclusion: "pending"`、`phase3SignOff` 对象下全部布尔子字段为 `false`、`materialsSha256: ""`
   - 维护阶段 AI 不得将上述字段自动改为通过值；只有当用户在对话中**明确提供人工核验证据（截图/签字/扫描件）并明确给出修改指令**时，AI 才允许逐字段修改为通过值；每次修改门禁字段都必须在输出中注明："已根据人工指令修改门禁字段，此操作不自动触发 status 变更"

## 九、输出要求

使用本 Skill 时，输出应满足以下要求：

- 明确说明当前正在处理的版本号
- 明确说明本次属于初始化、维护还是巡检
- 明确区分必须脚本化事项与允许人工操作事项
- 明确列出新增或补齐的文件
- 明确列出仍需人工确认或补充的信息

## 十、重要限制

- 不得用 Git 信息替代版本配置文件中的版本号
- 不得把可通过数据库完成的事项降级为人工操作
- 不得只生成脚本而不维护更新手册
- 不得只维护文档而不补齐必要脚本
- 不得在版本目录下继续扩展多级脚本子目录
- 不得在发布材料中保留模糊、无法执行、无法验证的表述
- **（一票否决红线）不得在无人明确指令的情况下自动修改 `release/version.json` 的 `version` 字段**
- **（一票否决红线）不得因开发环境代码变更、功能新增、缺陷修复、配置调整等任何场景自动 bump 或自动升级版本号**
- **（一票否决红线）初始化创建版本配置文件时，如无人工明确指出版本号，不得擅自填入具体版本号，必须使用占位值并提示人工维护**
- **（一票否决红线）维护阶段发现版本号需要变更时，必须向用户明确提示等待人工指令，不得自行写入推测性的版本号变更**
