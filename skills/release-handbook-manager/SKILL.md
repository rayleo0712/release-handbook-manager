# 版本发布手册管理

本 Skill 用于在项目内建立并维护一套可复用的版本发布治理机制，覆盖版本号管理、更新手册维护、数据库与配置脚本沉淀、发布检查、发布后验证、版本更新日志整理等工作。

## 适用前提

- 本 Skill 以“AI 深度参与开发过程”为主要适用前提
- 最适合 AI 持续参与需求分析、代码实现、改动整理和发布收口的协同开发场景
- 如果项目基本不用 AI 开发，或只在临近发版时少量使用 AI，不适合使用本 Skill
- 在低 AI 参与场景下，不得把本 Skill 表述为能够自动完整识别全部功能变化、所需 SQL、脚本与发布步骤

## 别名约定

- 聊天中的简称统一为：`rhm`
- `rhm` 等同于 `release-handbook-manager`
- 当用户在对话中提到 `rhm` 时，应按本 Skill 处理

当用户提出以下需求时，应优先启用本 Skill：

- 初始化项目的版本发布治理能力
- 在项目中创建版本配置文件
- 在项目中创建版本发布相关规则
- 为当前版本建立或补齐发布材料
- 在开发过程中持续登记当前版本的发布变更
- 整理当前版本的数据库脚本、配置脚本、人工操作步骤
- 在准备发布前检查版本材料是否完整
- 根据当前版本材料生成发布检查清单、发布后验证记录、版本更新日志

## 一、核心目标

本 Skill 不是只生成一份发布文档，而是要把以下机制真正落到项目内：

1. 项目内必须有唯一版本配置文件，作为当前版本号真源
2. 每个版本必须有唯一更新手册，作为当前版本发布内容真源
3. 凡是可通过数据库执行的变更，必须脚本化
4. 凡是不能脚本化但又必须执行的事项，必须登记为人工操作步骤
5. 发布时必须按版本手册逐步执行，而不是依赖口头说明或聊天记录
6. 版本更新日志应从当前版本更新手册中提炼生成

### 重要边界说明

- 本 Skill 不具备独立的“版本差异自动分析引擎”
- 本 Skill 不会凭空知道未留痕的功能变化、数据库变更、配置变化或人工操作项
- 只有在 AI 已持续参与开发过程、并掌握较完整上下文时，才更适合辅助生成 SQL、脚本、发布步骤和版本更新日志
- 当 AI 参与较少时，不适合使用本 Skill

## 二、版本号规则

### 2.1 唯一真源

- 当前版本号只能以 `release/version.json` 为唯一真源
- 禁止以 Git 提交记录、分支名、Tag 名等作为版本号唯一依据

### 2.2 格式约束

- 版本号格式固定为：`v主版本.次版本.修订号`
- 示例：
  - `v1.0.0`
  - `v1.3.2`
  - `v2.5.1`

### 2.3 维护原则

- 每次进入新的开发迭代或发布周期前，必须先维护 `release/version.json`
- 当前版本涉及的手册、脚本、发布检查、验证记录、更新日志，均必须归属于该版本号

### 2.4 版本号人工维护强制约束（一票否决红线）

**本条为一票否决级别的强制约束，违反即视为 Skill 执行失败：**

- `release/version.json` 中的 `version` 字段必须由人工明确指令触发维护，AI 不得在任何场景下自动生成或自动升级版本号，包括但不限于：
  - 开发环境代码变更后，AI 不得自动 bump 版本号
  - 新增功能、修复缺陷、调整配置后，AI 不得自行修改 `version` 字段
  - 初始化版本配置文件时，如无人工明确指定版本号，AI 只能使用占位模板（如 `vX.Y.Z` 或留空）并明确提示人工填写，不得擅自填入猜测的版本号
  - 维护阶段 AI 不得以任何形式的"智能版本建议"替代人工确认流程

- AI 仅允许在以下**两种**场景下操作 `version` 字段：
  1. 人工在对话中**明确给出具体目标版本号**并要求写入时，AI执行写操作
  2. 人工在对话中**明确指令版本号变更意图（如"把版本升级到 v1.2.3），AI 才可以执行写操作

- 除上述两种场景外，AI 发现版本号需要变更需求时，必须：
  - 立即停止自动写操作
  - 向用户明确提示："版本号必须人工维护，请给出明确指令后再执行"
  - 不得写入任何推测性的版本号变更

## 三、标准目录结构

首次初始化项目发布治理能力时，应创建如下结构：

```text
release/
  version.json
  versions/
    v1.0.0/
      01-更新手册.md
      02-db-001-数据库结构变更.sql
      02-db-002-历史数据修复.sql
      03-config-001-菜单权限配置.sql
      03-config-002-角色权限配置.sql
      04-发布检查清单.md
      05-发布后验证记录.md
      05-1-功能验收用例(非技术版).md
      06-版本更新日志.md
```

### 3.1 目录结构约束

- 当前版本目录统一为：`release/versions/{版本号}/`
- 当前版本目录采用单层平铺结构
- 禁止为 `02`、`03` 再建立多级子目录，避免执行发布时误操作
- **明确禁止**在 `versions/` 目录（含子目录）下存放任何 `YYYYMMDD-Windows-Terminal` 类临时命令文件、零散 PowerShell 脚本片段、临时命令笔记等；此类内容**必须合并写入** `01-更新手册.md §4.1.3 Windows PowerShell` 小节统一管理

### 3.2 文件编号含义（7类标准文件，05/05-1双轨配套缺一不可）

当前版本目录下标准文件共 7 类（编号：01/02/03/04/05/05-1/06），其中 `05` 与 `05-1` 为双轨配套文件，**缺一不可**，不得单独生成其中之一。

- `01-更新手册.md`：当前版本唯一真源，负责汇总发布材料（含脚本索引、人工操作、PowerShell命令、附件清单、签字区等）
- `02-db-xxx-说明.sql`：数据库类脚本（结构变更/历史数据修复等）
- `03-config-xxx-说明.sql`：配置类脚本（菜单/权限/角色/字典/参数等）
- `04-发布检查清单.md`：发布前检查材料（Checklist 真源）
- `05-发布后验证记录.md`：发布后技术验证真源（**仅限**测试/开发人员使用，覆盖 SQL 执行结果、代码自检、错误码校验、并发压测、缓存命中、denorm 回填、双写对账等全部技术维度验证）
- `05-1-功能验收用例(非技术版).md`：发布后非技术验收真源（面向产品经理/最终用户/UAT 验收人员，采用页面/操作/预期三段式，**不得出现任何技术术语**）；与 `05` 形成双轨：技术验证用 `05`，业务/UAT 验收用 `05-1`，两者互补、互不替代、必须同时生成
- `06-版本更新日志.md`：面向正式发布说明的版本日志（双面结构：对外业务面+对内技术面）

## 四、必须脚本化与允许人工操作的边界

### 4.1 必须脚本化

凡是本质上可以通过数据库执行完成的变更，必须提供可执行 SQL 脚本，不允许只写文字说明。

以下内容必须脚本化：

- 数据库表结构变更
- 字段新增、修改、删除
- 主键、外键、索引、约束调整
- 存储过程变更
- 触发器变更
- 历史数据修复、回填、迁移
- 菜单配置
- 菜单下权限配置
- 角色权限分配
- 其他可通过数据库增删改查直接完成的系统配置

补充原则：

- 菜单、权限、角色权限等虽然可在页面上人工配置，但其底层本质是数据库操作，因此必须归类为脚本化
- 不允许只写“请去页面手工配置菜单/权限”这类模糊说明

### 4.2 允许人工操作

仅以下场景允许保留为人工操作步骤：

- 修改已有配置文件的内容调整（不含新增配置文件）
- 生产环境配置类操作
- 确实无法脚本化的事项

凡归类为人工操作的事项，必须明确登记：

- 操作入口
- 操作顺序
- 操作内容
- 目标结果
- 校验方式

禁止使用以下模糊表述：

- “现场处理”
- “按实际情况调整”
- “发布时再看”

## 五、首次初始化时必须创建的内容

当项目尚未具备这套机制时，本 Skill 应优先初始化以下内容。

### 5.1 版本配置文件

路径：

```text
release/version.json
```

推荐模板：

```json
{
  "version": "v1.0.0",
  "previousVersion": "",
  "releaseDate": "",
  "status": "developing",
  "owner": "",
  "description": "",
  "releaseGate": {
    "checklist04AllPassed": false,
    "uat051Conclusion": "pending",
    "phase3SignOff": {
      "dev": false,
      "test": false,
      "ops": false
    },
    "materialsSha256": ""
  }
}
```

字段说明：

- `version`：当前版本号
- `previousVersion`：上一版本号
- `releaseDate`：正式发布日期，未发布可为空
- `status`：固定为 `developing` / `released`；**AI 不得自动修改此字段，必须严格遵守 §8.5 门禁门槛**
- `owner`：当前版本负责人（仅 owner 本人有权限发人工指令触发 status → released）
- `description`：当前版本一句话说明
- `releaseGate`：**版本门禁字段（顶层对象，AI 不得自动置为通过）**，四个子字段含义见 §8.5：
  - `releaseGate.checklist04AllPassed`：`04-发布检查清单.md` 全部 Checklist 项是否已人工核验通过（布尔值 true/false）
  - `releaseGate.uat051Conclusion`：`05-1` UAT 验收结论，枚举值：`pending`（待验收）/ `passed`（全部通过）/ `partial`（部分通过）/ `failed`（不通过）
  - `releaseGate.phase3SignOff`：签字门禁对象；其下各布尔子字段由项目按实际签字步骤定义（如 `dev/test/ops` 或 `p4aToP4bSigned/p4bToP4cSigned/finalPhysicalDropSigned`），**仅当所有子字段均为 `true` 时才视为通过**
  - `releaseGate.materialsSha256`：核心发布材料校验值；用于校验 `01/04/05/05-1/06` 等关键材料是否与待发布版本一致，默认空字符串，未人工回填前不得视为通过

### 5.2 项目内规则文件

应在项目规则目录中创建一份“版本发布与更新手册规则”文件，用于长期约束项目协作。

推荐位置：

```text
.trae/rules/YYYYMMDD-08-协作-版本发布与更新手册规则.md
```

规则文件应至少覆盖以下内容：

- 版本号唯一真源规则
- 版本材料目录规则
- 更新手册唯一真源规则
- 强制登记范围规则
- 必须脚本化规则
- 允许人工操作规则
- 发布执行规则
- 更新日志沉淀规则
- 发布材料完整性规则
- 维护责任规则

### 5.3 当前版本目录

应根据 `release/version.json` 中的版本号创建当前版本目录：

```text
release/versions/{版本号}/
```

### 5.4 当前版本模板文件清单（必须同时生成 05/05-1 双轨模板）

应在当前版本目录下**强制同时补齐以下 5 个模板文件**（其中 05/05-1 必须成对生成，缺一不可）：

- `01-更新手册.md`
- `04-发布检查清单.md`
- `05-发布后验证记录.md`
- `05-1-功能验收用例(非技术版).md`
- `06-版本更新日志.md`

必要时根据当前版本需求创建：

- `02-db-001-xxx.sql`
- `03-config-001-xxx.sql`

**初始化阶段强制约束（关于 05-1）：**

- `05-1` 模板中 §八「验收汇总表」的 P0/P1/P2 计数行（含合计数字）**必须全部留空，不得预填任何数字**；数字回填操作必须在验收启动前，按 §6.3.1(f) 约定的两条 PowerShell 命令人工执行回填

## 六、更新手册与配套模板

### 6.1 `01-更新手册.md`

职责：

- 作为当前版本唯一真源
- 记录本版本全部变更事项
- 编排发布执行顺序
- 记录脚本、人工操作、回滚方案、附件清单

推荐结构：

```md
# {版本号} 更新手册

## 1. 基本信息
- 版本号：
- 上一版本号：
- 当前状态：
- 版本负责人：
- 计划发布时间：

## 2. 本版本变更摘要
### 2.1 新增功能
### 2.2 功能调整
### 2.3 缺陷修复
### 2.4 兼容性处理
### 2.5 风险说明

## 3. 必须脚本化的变更
### 3.1 数据库结构变更
### 3.2 历史数据修复 / 回填 / 迁移
### 3.3 菜单 / 权限 / 角色权限 / 字典 / 参数 / 流程配置

## 4. 允许人工操作的事项
### 4.1 修改已有配置文件
### 4.2 生产环境配置调整
### 4.3 其他确实无法脚本化的事项

## 5. 发布执行步骤
## 6. 回滚方案
## 7. 发布前检查关键项
## 8. 发布后验证关键项
## 9. 发布通知与沟通计划
## 10. 发布后观察期安排
## 11. 发布角色 × 真源文件索引表
## 12. 附件清单
## 13. 签字区
```

### 6.2 `04-发布检查清单.md`

职责：

- 在正式发布前核对版本号、脚本、手册、人工操作、回滚方案是否齐全

建议检查项至少包括：

- `release/version.json` 是否已更新
- 版本号格式是否正确
- 当前版本目录是否已创建
- 更新手册是否已补充完整
- 所有数据库变更是否均已生成 `02-db-xxx` 脚本
- 所有配置类数据库操作是否均已生成 `03-config-xxx` 脚本
- 所有人工操作事项是否已明确登记
- 发布执行顺序、发布后验证、回滚方案是否已确认

### 6.3 `05-发布后验证记录.md`（技术版规范保留）

职责：

- 记录正式发布后的执行结果和验证结果（**面向测试/开发人员的技术版验证记录真源**）
- **仅限**测试/开发人员使用，不对产品/用户/UAT 交付

建议至少覆盖：

- 数据库脚本执行结果
- 配置脚本执行结果
- 人工操作执行结果
- 核心功能验证结果
- 菜单权限验证结果
- 数据结果验证
- 页面显示验证
- 日志记录验证
- 异常与处理
- 最终结论

---

### 6.3.1 `05-1-功能验收用例(非技术版).md`（专项规范扩充）

职责：

- 面向产品经理、最终用户、UAT 验收人员等**非技术角色**的功能验收手册真源
- 与 `05-发布后验证记录.md` 形成**双轨配套，缺一不可**：`05` 是技术验证真源，`05-1` 是非技术验收真源，两者互补、互不替代、必须同时生成
- 所有描述必须使用**业务语言**，禁止出现 SQL、错误码、代码路径、并发、缓存、双写、回滚、tenantId、denorm 等技术术语
- 采用「页面 / 操作 / 预期」三段式结构，附加执行追踪列

---

**(a) 内容来源范围（必须严格遵守）：**

1. **主要来源**：`01-更新手册.md §2 变更摘要` 中的「新增功能」与「功能调整」（用户可感知的业务功能）
2. **辅助来源**：`06-版本更新日志.md §1 核心能力新增`（提取页面路径和用户操作视角）
3. **必须包含**：`01-更新手册.md §2.3 缺陷修复` 中所有**用户可感知**的缺陷修复，需转化为回归验收用例
4. **明确排除**：以下内容**不得**出现在 05-1 中：
   - 数据库脚本执行结果、SQL 校验
   - 组织结构双写对账、P4-A/B/C 灰度开关、PHASE 切换
   - 错误码校验（40093~40099、40310、40311~40315、40901-40902、50001 等）
   - 代码路径自检、代码批次（B1/P3/P4A/P4B/P4C/S01 等）
   - 并发压测、幂等校验、缓存命中
   - denorm 回填、审计日志字段、乐观锁
   - 任何纯后台技术逻辑的验证

---

**(b) 用例组织方式：**

- 按「业务模块 → 子功能 → 用例」三级组织
- 业务模块命名必须使用用户熟悉的业务术语，不得使用内部开发代号
- 每个业务模块下的子功能顺序与 `01-更新手册.md §2` 保持一致

---

**(c) 用例覆盖深度（完整级，5 类场景保留）：**

- 每个子功能至少覆盖以下 5 类场景：
  1. **主流程正向用例**（P0）：最常见的顺利完成路径
  2. **审批驳回用例**（P1）：若涉及审批流程，必须包含被驳回的用例
  3. **边界/互斥用例**（P1）：重复提交、状态不允许时操作被拦截等
  4. **列表查询用例**（P1）：按关键字段筛选、分页、排序
  5. **回归验证用例**（P1）：对应缺陷修复的回归验收
- 缺陷修复用例需在「操作」列明确描述触发缺陷修复前的原始场景，「预期」列描述修复后的正确表现

---

**(d) 输出模式开关（二选一，生成时必须在文档首部明确标注）：**

   - (7) **汇总表留空核验（新增）**：05-1 §八「验收汇总表」中 P0/P1/P2 计数（含合计行）在验收启动前**是否保持留空状态**；如已预填任何数字（即使是正确数字）也**直接判定不合规**，必须清除后置位空值，由两条 PowerShell 命令在验收前回填
   - (8) **双轨说明核验（新增）**：05-1 文档首部是否存在「双轨覆盖关系说明 4 条」完整文字（逐字比对 §6.3.1 建议首部结构中的 4 条说明）；缺失任一条即视为不合规

## 八、操作判断原则

### 8.1 何时应直接初始化

以下情况优先执行初始化：

- 项目内还没有 `release/version.json`
- 项目内还没有版本发布相关规则文件
- 用户明确要求建立版本发布治理机制
- 用户明确要求创建版本更新手册体系

### 8.2 何时应进入维护模式

以下情况优先进入维护模式：

- 项目中已存在版本配置文件与版本目录
- 用户要求补登记当前版本的变更事项
- 用户要求为当前改动补 SQL 脚本、发布清单、更新日志

### 8.3 何时应进入巡检模式

以下情况优先进入巡检模式：

- 用户要求准备发版
- 用户要求检查某个版本材料是否完整
- 用户要求核对当前版本是否缺少脚本、手册或验证记录

---

### 8.4 一票否决级 · 版本号人工维护 4 条红线（原文保留）

**本条为一票否决级别的强制约束，违反即视为 Skill 执行失败：**

1. `release/version.json` 中的 `version` 字段必须由人工明确指令触发维护，AI 不得在任何场景下自动生成或自动升级版本号（开发环境变更后不得自动 bump、功能/缺陷/配置调整后不得自行修改、初始化无人工指令时只能用占位模板、不得以任何"智能版本建议"替代人工确认）。
2. AI 仅允许在以下**两种**场景下操作 `version` 字段：① 人工明确给出具体目标版本号并要求写入；② 人工明确指令版本号变更意图（如"把版本升级到 v1.2.3"）。
3. 除上述两种场景外，AI 发现版本号需要变更需求时，必须立即停止自动写操作，向用户明确提示："版本号必须人工维护，请给出明确指令后再执行"，不得写入任何推测性变更。
4. 初始化创建版本配置文件时，如无人工明确指出版本号，不得擅自填入具体版本号，必须使用占位值（`vX.Y.Z` 或空字符串）并提示人工维护。

---

### 8.5 一票否决级 · 版本门禁字段（releaseGate 门槛规则）

> **前置依赖**：`release/version.json` 顶层必须存在 `releaseGate` 对象，至少包含以下四个字段（详见 §5.1 模板）；门禁字段满足要求 + 人工 owner 指令 = AI 方可操作 `status` 字段，否则一律禁止。

**门禁字段定义（4 个，缺一不可）：**

| 字段路径 | 类型 | 通过门槛值 | 含义 |
|---|---|---|---|
| `releaseGate.checklist04AllPassed` | `boolean` | **`true`** | `04-发布检查清单.md` 全部 Checklist 条目已由人工逐项核验签字通过；`false` = 仍有未通过项 |
| `releaseGate.uat051Conclusion` | `string`（枚举） | **`"passed"`** | `05-1` 验收结论：`pending`=待验收 / `passed`=**全部通过（门槛值）** / `partial`=部分通过 / `failed`=不通过；仅 `passed` 视为达标 |
| `releaseGate.phase3SignOff` | `object` | **对象下全部布尔子字段 = `true`** | 项目级签字门禁对象；可按项目定义为 `dev/test/ops`，也可定义为 `p4aToP4bSigned/p4bToP4cSigned/finalPhysicalDropSigned`；仅当对象下全部布尔子字段均为 `true` 时视为通过 |
| `releaseGate.materialsSha256` | `string` | **非空，且与待发布材料校验值一致** | 核心发布材料校验值；空字符串或校验不一致均视为未通过 |

**status 变更强制规则（违反视为 Skill 执行失败）：**

1. **允许 AI 执行 `status: "developing" → "released"` 的唯一组合条件（必须 100% 同时满足）：**
   - ✅ `releaseGate.checklist04AllPassed === true`
   - ✅ `releaseGate.uat051Conclusion === "passed"`
   - ✅ `releaseGate.phase3SignOff` 对象下全部布尔子字段均为 `true`
   - ✅ `releaseGate.materialsSha256` 非空，且已由人工确认与待发布材料校验值一致
   - ✅ 当前对话中，`release/version.json` 中的 `owner` 字段对应本人（即版本负责人）**在对话中明确发出人工指令**，例如："请把 v1.2.3 状态改为 released" / "v1.2.3 正式发布，更新 status"
   - 以上五项**有任意一项未达标，AI 必须立即停止写操作**，逐条向用户输出未通过的门禁字段及原因，不得修改 `status`。

2. **禁止任何场景下的自动 status 变更：**
   - AI 不得因巡检通过、脚本齐全、用例通过等任何自动判断结果，主动或自动修改 `status`
   - 非 owner（即对话人 ≠ `owner` 字段登记的负责人）发指令要求改 status 时，AI 必须明确拒绝："本版本号门禁仅允许 owner 本人发人工指令触发 status → released，请联系版本负责人 {owner} 本人操作"
   - 反向变更 `status: "released" → "developing"`（撤回发布）同样需要 owner 本人明确人工指令，AI 不得自动回退

3. **初始化/维护阶段 releaseGate 默认值约束：**
   - 初始化生成 `version.json` 时，`releaseGate` 字段**必须固定写入门槛否定值**：`checklist04AllPassed: false`、`uat051Conclusion: "pending"`、`phase3SignOff` 对象下全部布尔子字段为 `false`、`materialsSha256: ""`
   - 维护阶段 AI 不得将上述字段自动改为通过值；只有当用户在对话中**明确提供人工核验证据（截图/签字/扫描件）并明确给出修改指令**时，AI 才允许逐字段修改为通过值；每次修改门禁字段都必须在输出中注明："已根据人工指令修改门禁字段，此操作不自动触发 status 变更"

## 九、输出要求

使用本 Skill 时，输出应满足以下要求：

- 明确说明当前正在处理的版本号
- 明确说明本次属于初始化、维护还是巡检
- 明确区分必须脚本化事项与允许人工操作事项
- 明确列出新增或补齐的文件
- 明确列出仍需人工确认或补充的信息

## 十、重要限制

- 不得用 Git 信息替代版本配置文件中的版本号
- 不得把可通过数据库完成的事项降级为人工操作
- 不得只生成脚本而不维护更新手册
- 不得只维护文档而不补齐必要脚本
- 不得在版本目录下继续扩展多级脚本子目录
- 不得在发布材料中保留模糊、无法执行、无法验证的表述
- **（一票否决红线）不得在无人明确指令的情况下自动修改 `release/version.json` 的 `version` 字段**
- **（一票否决红线）不得因开发环境代码变更、功能新增、缺陷修复、配置调整等任何场景自动 bump 或自动升级版本号**
- **（一票否决红线）初始化创建版本配置文件时，如无人工明确指出版本号，不得擅自填入具体版本号，必须使用占位值并提示人工维护**
- **（一票否决红线）维护阶段发现版本号需要变更时，必须向用户明确提示等待人工指令，不得自行写入推测性的版本号变更**
