# 版本发布手册管理

本 Skill 用于在项目内建立并维护一套可复用的版本发布治理机制，覆盖版本号管理、更新手册维护、数据库与配置脚本沉淀、发布检查、发布后验证、版本更新日志整理等工作。

## 适用前提

- 本 Skill 以“AI 深度参与开发过程”为主要适用前提
- 最适合 AI 持续参与需求分析、代码实现、改动整理和发布收口的协同开发场景
- 如果项目基本不用 AI 开发，或只在临近发版时少量使用 AI，不适合使用本 Skill
- 在低 AI 参与场景下，不得把本 Skill 表述为能够自动完整识别全部功能变化、所需 SQL、脚本与发布步骤

## 别名约定

- 聊天中的简称统一为：`rhm`
- `rhm` 等同于 `release-handbook-manager`
- 当用户在对话中提到 `rhm` 时，应按本 Skill 处理

当用户提出以下需求时，应优先启用本 Skill：

- 初始化项目的版本发布治理能力
- 在项目中创建版本配置文件
- 在项目中创建版本发布相关规则
- 为当前版本建立或补齐发布材料
- 在开发过程中持续登记当前版本的发布变更
- 整理当前版本的数据库脚本、配置脚本、人工操作步骤
- 在准备发布前检查版本材料是否完整
- 根据当前版本材料生成发布检查清单、发布后验证记录、版本更新日志

## 一、核心目标

本 Skill 不是只生成一份发布文档，而是要把以下机制真正落到项目内：

1. 项目内必须有唯一版本配置文件，作为当前版本号真源
2. 每个版本必须有唯一更新手册，作为当前版本发布内容真源
3. 凡是可通过数据库执行的变更，必须脚本化
4. 凡是不能脚本化但又必须执行的事项，必须登记为人工操作步骤
5. 发布时必须按版本手册逐步执行，而不是依赖口头说明或聊天记录
6. 版本更新日志应从当前版本更新手册中提炼生成

### 重要边界说明

- 本 Skill 不具备独立的“版本差异自动分析引擎”
- 本 Skill 不会凭空知道未留痕的功能变化、数据库变更、配置变化或人工操作项
- 只有在 AI 已持续参与开发过程、并掌握较完整上下文时，才更适合辅助生成 SQL、脚本、发布步骤和版本更新日志
- 当 AI 参与较少时，不适合使用本 Skill

## 二、版本号规则

### 2.1 唯一真源

- 当前版本号只能以 `release/version.json` 为唯一真源
- 禁止以 Git 提交记录、分支名、Tag 名等作为版本号唯一依据

### 2.2 格式约束

- 版本号格式固定为：`v主版本.次版本.修订号`
- 示例：
  - `v1.0.0`
  - `v1.3.2`
  - `v2.5.1`

### 2.3 维护原则

- 每次进入新的开发迭代或发布周期前，必须先维护 `release/version.json`
- 当前版本涉及的手册、脚本、发布检查、验证记录、更新日志，均必须归属于该版本号

## 三、标准目录结构

首次初始化项目发布治理能力时，应创建如下结构：

```text
release/
  version.json
  versions/
    v1.0.0/
      01-更新手册.md
      02-db-001-数据库结构变更.sql
      02-db-002-历史数据修复.sql
      03-config-001-菜单权限配置.sql
      03-config-002-角色权限配置.sql
      04-发布检查清单.md
      05-发布后验证记录.md
      06-版本更新日志.md
```

### 3.1 目录结构约束

- 当前版本目录统一为：`release/versions/{版本号}/`
- 当前版本目录采用单层平铺结构
- 禁止为 `02`、`03` 再建立多级子目录，避免执行发布时误操作

### 3.2 文件编号含义

- `01-更新手册.md`：当前版本唯一真源，负责汇总发布材料
- `02-db-xxx-说明.sql`：数据库类脚本
- `03-config-xxx-说明.sql`：配置类脚本
- `04-发布检查清单.md`：发布前检查材料
- `05-发布后验证记录.md`：发布后验证材料
- `06-版本更新日志.md`：面向正式发布说明的版本日志

## 四、必须脚本化与允许人工操作的边界

### 4.1 必须脚本化

凡是本质上可以通过数据库执行完成的变更，必须提供可执行 SQL 脚本，不允许只写文字说明。

以下内容必须脚本化：

- 数据库表结构变更
- 字段新增、修改、删除
- 主键、外键、索引、约束调整
- 存储过程变更
- 触发器变更
- 历史数据修复、回填、迁移
- 菜单配置
- 菜单下权限配置
- 角色权限分配
- 其他可通过数据库增删改查直接完成的系统配置

补充原则：

- 菜单、权限、角色权限等虽然可在页面上人工配置，但其底层本质是数据库操作，因此必须归类为脚本化
- 不允许只写“请去页面手工配置菜单/权限”这类模糊说明

### 4.2 允许人工操作

仅以下场景允许保留为人工操作步骤：

- 修改已有配置文件的内容调整（不含新增配置文件）
- 生产环境配置类操作
- 确实无法脚本化的事项

凡归类为人工操作的事项，必须明确登记：

- 操作入口
- 操作顺序
- 操作内容
- 目标结果
- 校验方式

禁止使用以下模糊表述：

- “现场处理”
- “按实际情况调整”
- “发布时再看”

## 五、首次初始化时必须创建的内容

当项目尚未具备这套机制时，本 Skill 应优先初始化以下内容。

### 5.1 版本配置文件

路径：

```text
release/version.json
```

推荐模板：

```json
{
  "version": "v1.0.0",
  "previousVersion": "",
  "releaseDate": "",
  "status": "developing",
  "owner": "",
  "description": ""
}
```

字段说明：

- `version`：当前版本号
- `previousVersion`：上一版本号
- `releaseDate`：正式发布日期，未发布可为空
- `status`：建议固定为 `developing` / `released`
- `owner`：当前版本负责人
- `description`：当前版本一句话说明

### 5.2 项目内规则文件

应在项目规则目录中创建一份“版本发布与更新手册规则”文件，用于长期约束项目协作。

推荐位置：

```text
.trae/rules/YYYYMMDD-08-协作-版本发布与更新手册规则.md
```

规则文件应至少覆盖以下内容：

- 版本号唯一真源规则
- 版本材料目录规则
- 更新手册唯一真源规则
- 强制登记范围规则
- 必须脚本化规则
- 允许人工操作规则
- 发布执行规则
- 更新日志沉淀规则
- 发布材料完整性规则
- 维护责任规则

### 5.3 当前版本目录

应根据 `release/version.json` 中的版本号创建当前版本目录：

```text
release/versions/{版本号}/
```

### 5.4 当前版本模板文件

应在当前版本目录下补齐：

- `01-更新手册.md`
- `04-发布检查清单.md`
- `05-发布后验证记录.md`
- `06-版本更新日志.md`

必要时根据当前版本需求创建：

- `02-db-001-xxx.sql`
- `03-config-001-xxx.sql`

## 六、更新手册与配套模板

### 6.1 `01-更新手册.md`

职责：

- 作为当前版本唯一真源
- 记录本版本全部变更事项
- 编排发布执行顺序
- 记录脚本、人工操作、回滚方案、附件清单

推荐结构：

```md
# {版本号} 更新手册

## 1. 基本信息
- 版本号：
- 上一版本号：
- 当前状态：
- 版本负责人：
- 计划发布时间：

## 2. 本版本变更摘要
### 2.1 新增功能
### 2.2 功能调整
### 2.3 缺陷修复
### 2.4 兼容性处理
### 2.5 风险说明

## 3. 必须脚本化的变更
### 3.1 数据库结构变更
### 3.2 历史数据修复 / 回填 / 迁移
### 3.3 菜单 / 权限 / 角色权限 / 字典 / 参数 / 流程配置

## 4. 允许人工操作的事项
### 4.1 修改已有配置文件
### 4.2 生产环境配置调整
### 4.3 其他确实无法脚本化的事项

## 5. 发布执行步骤
## 6. 回滚方案
## 7. 附件清单
```

### 6.2 `04-发布检查清单.md`

职责：

- 在正式发布前核对版本号、脚本、手册、人工操作、回滚方案是否齐全

建议检查项至少包括：

- `release/version.json` 是否已更新
- 版本号格式是否正确
- 当前版本目录是否已创建
- 更新手册是否已补充完整
- 所有数据库变更是否均已生成 `02-db-xxx` 脚本
- 所有配置类数据库操作是否均已生成 `03-config-xxx` 脚本
- 所有人工操作事项是否已明确登记
- 发布执行顺序、发布后验证、回滚方案是否已确认

### 6.3 `05-发布后验证记录.md`

职责：

- 记录正式发布后的执行结果和验证结果

建议至少覆盖：

- 数据库脚本执行结果
- 配置脚本执行结果
- 人工操作执行结果
- 核心功能验证结果
- 菜单权限验证结果
- 数据结果验证
- 页面显示验证
- 日志记录验证
- 异常与处理
- 最终结论

### 6.4 `06-版本更新日志.md`

职责：

- 作为对内或对外发布说明的沉淀结果
- 优先从 `01-更新手册.md` 提炼生成

建议至少覆盖：

- 新增功能
- 功能优化
- 问题修复
- 数据与配置调整
- 兼容性说明

## 七、执行工作流

启用本 Skill 后，应按以下顺序工作。

### 7.1 初始化阶段

1. 检查项目是否已存在 `release/version.json`
2. 检查项目是否已存在版本发布相关规则文件
3. 检查当前版本目录是否存在
4. 若缺失，则自动初始化版本配置文件、规则文件、版本目录与模板文件

### 7.2 维护阶段

1. 读取当前版本号
2. 判断本次需求是否涉及：
   - 数据库结构变更
   - 历史数据修复/回填
   - 菜单权限配置
   - 角色权限配置
   - 字典/参数/流程/模板配置
   - 已有配置文件调整
   - 生产环境配置调整
   - 其他人工操作
3. 根据类型决定：
   - 必须脚本化
   - 允许人工操作
4. 追加或创建对应脚本与更新手册内容
5. 同步补充发布检查清单、发布后验证记录、版本更新日志所需内容

### 7.3 发布前巡检阶段

1. 检查版本号与目录是否一致
2. 检查脚本编号是否连续、用途是否清晰
3. 检查更新手册是否记录全部变更
4. 检查人工操作是否具备明确步骤与校验方式
5. 检查发布后验证与回滚方案是否完整

## 八、操作判断原则

### 8.1 何时应直接初始化

以下情况优先执行初始化：

- 项目内还没有 `release/version.json`
- 项目内还没有版本发布相关规则文件
- 用户明确要求建立版本发布治理机制
- 用户明确要求创建版本更新手册体系

### 8.2 何时应进入维护模式

以下情况优先进入维护模式：

- 项目中已存在版本配置文件与版本目录
- 用户要求补登记当前版本的变更事项
- 用户要求为当前改动补 SQL 脚本、发布清单、更新日志

### 8.3 何时应进入巡检模式

以下情况优先进入巡检模式：

- 用户要求准备发版
- 用户要求检查某个版本材料是否完整
- 用户要求核对当前版本是否缺少脚本、手册或验证记录

## 九、输出要求

使用本 Skill 时，输出应满足以下要求：

- 明确说明当前正在处理的版本号
- 明确说明本次属于初始化、维护还是巡检
- 明确区分必须脚本化事项与允许人工操作事项
- 明确列出新增或补齐的文件
- 明确列出仍需人工确认或补充的信息

## 十、重要限制

- 不得用 Git 信息替代版本配置文件中的版本号
- 不得把可通过数据库完成的事项降级为人工操作
- 不得只生成脚本而不维护更新手册
- 不得只维护文档而不补齐必要脚本
- 不得在版本目录下继续扩展多级脚本子目录
- 不得在发布材料中保留模糊、无法执行、无法验证的表述
