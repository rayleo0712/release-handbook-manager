### 6.5 自动化测试前置条件（与 `release-test-auto` 联动）

职责：

- 当项目希望由 AI 执行 UAT / 回归 / 发布前自动化测试时，当前版本发布材料必须提供足够的“自动化测试前置条件真源”
- `rhm` 负责把这些前置条件沉淀到当前版本材料中；真正执行自动化测试时，应调用独立 Skill：`release-test-auto`

强制要求：

1. **启动命令真源**

   - `04-发布检查清单.md` §8.1 启动命令表中必须记录当前项目在 IDE 终端或等价命令行中可直接执行的启动命令（命令本体只写在 04 §8，01 只写指向）
   - 启动命令必须与本次自动化测试范围匹配
   - 若执行的是页面级 UAT / UI 回归 / 端到端流程回归，则至少满足以下之一：
     - 一体化联调启动命令
     - 测试模式启动命令
     - 可分别启动前端与后端，且测试库 / 依赖服务已可用
   - 仅有前端启动命令、或仅有后端启动命令，不足以宣称可以稳定完成整链路自动化测试
   - 启动命令必须支持“修复 bug 后可再次从终端重启”，不得依赖人工点击 IDE 页面按钮
2. **数据基线真源**

   - `04-发布检查清单.md` §8.2 数据恢复命令表中必须记录测试数据库备份文件路径、恢复命令或恢复脚本路径（命令本体只写在 04 §8）
   - 必须明确恢复目标为测试库，禁止指向生产/准生产环境
   - 若项目计划让 AI 自动化测试反复执行，必须同时登记恢复后校验方式
3. **账号真源**

   - 当前版本 `05-1-功能验收用例(非技术版).md` 的 `## 2. 角色准备` 为自动化测试账号真源
   - `release-test-auto` 读取账号时，必须遵守“当前版本优先、上一个版本兜底、不得继续追溯更早历史版本”的规则
4. **用例覆盖真源**

   - 若当前版本计划执行 AI 自动化测试，则 `05-1` 不得只保留正向主流程
   - 每个关键业务模块至少应明确：
     - 1 条正向主流程
     - 1 条逆向权限/状态/输入场景（三选一或多选）
   - 若发布材料中逆向场景不足，执行阶段允许 `release-test-auto` 自动补充，但必须在测试报告中单独标记“AI 自动补充逆向场景”
5. **结果归档真源**

   - 自动化测试的最终结果必须回填到当前版本材料中：
     - `05-发布后验证记录.md`：记录技术执行结果、恢复校验、失败日志、脚本输出
     - `05-1-功能验收用例(非技术版).md`：回填用户可见结果、通过/不通过、截图路径、备注
   - 自动化测试过程中生成的结构化结果文件、截图、日志路径必须在 `05-发布后验证记录.md` 中登记，保证可追溯；过程中临时使用的命令一律登记到 `04-发布检查清单.md §8.5 临时命令记录`，不得另建命令文件
6. **两类型测试形态说明（与 rta 门控联动）**

   - `release-test-auto` 执行分为两阶段：类型一·快速测试（curl/API 层，默认全量）→ 类型二·渲染测试（Playwright，对应账号登录页面 1:1 操作）；门控规则、流程引擎 SQL 边界（禁 SQL 直推、夹具 API 推进）以 rta 的 `coverage-测试覆盖规则.md` §5/§6 为准，`rhm` 侧只负责账号与启动/基线前置齐全
   - 涉及流程引擎的系统，`05-1 §2 角色准备` 必须能支撑「流程节点 → 操作角色 → 测试账号」映射（见 `templates-05-1-功能验收用例.md` (d-1)），否则对应节点用例不可执行

联动规则：

- 当用户提出“AI 模拟人工测试 / 自动化回归 / 基于 05-1 自动执行验收 / 修复后重启续跑测试”等需求时：
  - `rhm` 负责先检查上述前置条件是否已经在当前版本材料中齐全
  - 若前置条件齐全，应明确建议或切换到 `release-test-auto`
  - 若前置条件不齐全，应先补齐当前版本材料，再进入自动化测试执行
