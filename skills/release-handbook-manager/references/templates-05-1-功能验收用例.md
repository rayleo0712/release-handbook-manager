### 6.3.1 `05-1-功能验收用例(非技术版).md`（专项规范扩充）

职责：

- 面向产品经理、最终用户、UAT 验收人员等**非技术角色**的功能验收手册真源
- 与 `05-发布后验证记录.md` 形成**双轨配套，缺一不可**：`05` 是技术验证真源，`05-1` 是非技术验收真源，两者互补、互不替代、必须同时生成
- 所有描述必须使用**业务语言**，禁止出现 SQL、错误码、代码路径、并发、缓存、双写、回滚、tenantId、denorm 等技术术语
- 采用「页面 / 操作 / 预期」三段式结构，附加执行追踪列
- `05-1` 是**当前项目的验收真源**，实际生成内容允许出现当前项目的页面名称、菜单路径、业务角色、用户可见文案，但 **Skill 规则、模板示例、推荐表头、占位样例中不得写死任何具体项目/客户/真实业务模块/真实账号/真实 URL/内部代号**

---

**(a) 内容来源范围（必须严格遵守）：**

1. **主要来源**：`01-更新手册.md §3 本版本变更摘要` 中的「§3.1 新增功能」与「§3.3 功能调整」（用户可感知的业务功能）
2. **辅助来源**：`06-版本更新日志.md §1 核心能力新增`（提取页面路径和用户操作视角）
3. **必须包含**：`01-更新手册.md §3.4 缺陷修复` 中所有**用户可感知**的缺陷修复，需转化为回归验收用例
4. **明确排除**：以下内容**不得**出现在 05-1 中：
   - 数据库脚本执行结果、SQL 校验
   - 任何内部发布批次、灰度开关、阶段代号、内部模块编号
   - 错误码、接口参数名、数据库表名、字段名、缓存键名等技术实现细节
   - 代码路径、分支名、脚本编号、内部环境名、内部部署标识
   - 并发压测、幂等校验、缓存命中率、性能调优、审计字段、锁机制
   - 任何纯后台技术逻辑的验证

---

**(b) 用例组织方式：**

- 按「业务模块 → 子功能 → 用例」三级组织
- 业务模块命名必须使用用户熟悉的业务术语，不得使用内部开发代号
- 每个业务模块下的子功能顺序与 `01-更新手册.md §3` 保持一致

---

**(c) 用例覆盖深度（完整级，5 类场景保留）：**

- 每个子功能至少覆盖以下 5 类场景：
  1. **主流程正向用例**（P0）：最常见的顺利完成路径
  2. **审批驳回用例**（P1）：若涉及审批流程，必须包含被驳回的用例
  3. **边界/互斥用例**（P1）：重复提交、状态不允许时操作被拦截等
  4. **列表查询用例**（P1）：按关键字段筛选、分页、排序
  5. **回归验证用例**（P1）：对应缺陷修复的回归验收
- 缺陷修复用例需在「操作」列明确描述触发缺陷修复前的原始场景，「预期」列描述修复后的正确表现

---

**(d) 输出模式开关（二选一，生成时必须在文档首部明确标注）：**

| 模式                             | 适用场景                               | 处理规则                                                                                                                        |
| --- | --- | --- |
| **A 内部协作模式（默认）** | 项目组内部协作、开发自测联调、内部评审 | **允许保留**少量通用追踪信息：如变更编号、覆盖类型、内部备注；但仍不得写代码路径、数据库字段、真实客户信息等技术/敏感信息 |
| **B 对外交付模式**         | 向客户/甲方/UAT 团队正式交付验收       | **必须清除全部内部追踪信息与内部备注**：变更编号、内部代号、内部备注等，仅保留纯业务语言描述与验收步骤                    |

- 默认采用 **A 内部协作模式**；切换为 B 模式时必须由人工明确指令触发

**(d-1) 角色准备区（生成时必须创建，不得省略）：**

- 在正式功能用例开始前，必须固定生成 `## 2. 角色准备` 小节，用于登记本次验收涉及的角色、账号与准备状态
- 该小节必须包含说明文字：`测试密码` 如未单独填写，默认按 `111111` 准备
- 角色准备表格必须至少包含以下 6 列，列顺序不得调整：
  - `角色`
  - `用途`
  - `测试账号`
  - `测试密码`
  - `是否已准备`
  - `备注`
- 填写要求：
  - `测试账号`：模板初始可留空，由现场实施/测试人员补录
  - `测试密码`：如现场未单独指定，默认填写 `111111`
  - `是否已准备`：使用勾选方式标记账号是否已就绪
- 若本次 05-1 涉及多角色审批、多岗位流转或角色切换验证，必须在该表中预置完整角色链，不得只放一个超管账号代替全流程
- **节点/角色 → 账号映射（与 rta 两类型测试联动）**：涉及流程引擎的系统，该表必须能支撑「流程节点 → 操作角色 → 测试账号」的完整映射——`角色` 列与节点办理角色一致，`备注` 列可标注对应节点（如「部门审批节点」）；rta 快速测试用该账号 token 发请求、渲染测试用该账号登录页面，缺映射即该节点用例不可执行
- **上一版本账号迁移规则（强制）**：
  - 生成当前版本 `05-1` 角色准备区时，必须先读取 `release/version.json` 中的 `previousVersion`
  - 仅允许检查**上一个版本**同名文件：`release/versions/{previousVersion}/05-1-功能验收用例(非技术版).md`
  - 若上一个版本同名文件存在，且其中 `## 2. 角色准备` 表格已填写 `测试账号` / `测试密码`，则生成当前版本时应**优先按同名角色迁移这两列信息**
  - 迁移匹配原则：以 `角色` 列文本完全一致作为匹配条件；只迁移 `测试账号`、`测试密码`，**不得**迁移 `是否已准备`、`备注`、历史勾选状态
  - 若上一个版本中某角色未填写密码或密码为空，则当前版本该角色默认仍按 `111111` 填写
  - 若 `previousVersion` 为空、上一个版本文件不存在、上一个版本无角色准备区，或找不到同名角色，则当前版本按模板默认值生成即可
  - **禁止**为补账号信息而继续追溯更早历史版本；只允许看上一个版本，不能看更久远版本

推荐结构：


**(e) 与变更台账映射规则（强制）：**

1. `05-1` 中每条用例必须填写 `来源变更编号`，不得留空
2. `来源变更编号` 必须能在 `01-更新手册.md §3.7 变更台账（唯一真源）` 中找到对应记录
3. 同一条变更至少应有 1 条 `主流程` 用例
4. 对用户可感知的重要功能变更，不得只生成主流程用例，必须结合业务风险补充 `逆向 / 异常 / 边界 / 回归 / 权限 / 状态流转` 中的适用类型
5. 当某条变更的 `当前有效摘要` 发生变化时，必须同步检查并更新该变更关联的全部 `05-1` 用例
6. 已标记为 `cancelled` 或 `merged` 的变更，不得继续作为新用例的 `来源变更编号`

**(f) 10 列固定列名（必须严格一致，不得增删改列名、不得调整列顺序）：**

05-1 中所有用例表格的列名与列顺序**必须严格为以下 10 列**，任何偏差视为不合规：

| 序号 | 固定列名（必须完全一致）     | 填写规范                                                                                                                                                               |
| --- | --- | --- |
| 1    | **用例编号**           | 格式：`模块缩写-序号`，如 `REG-001`、`UAT-012`，便于追踪与沟通                                                                                                   |
| 2    | **来源变更编号**       | 必须引用`01 §3.7 变更台账` 中已存在的 `变更编号`，如 `CHG-REG-001`                                                                                              |
| 3    | **覆盖类型**           | 固定枚举：`主流程 / 回归 / 逆向 / 异常 / 边界 / 权限 / 状态流转`                                                                                                     |
| 4    | **优先级(P0/P1/P2)**   | `P0`（冒烟必过，核心主流程）/ `P1`（重要功能，完整验收必过）/ `P2`（辅助或边界场景，可选）；**列名必须带括号注明取值范围**                                 |
| 5    | **页面(中文路径+URL)** | 菜单中文路径 + URL，格式：`一级菜单 > 二级菜单 > 页面名称（/xx/yy?param=zzz）`；**列名必须带括号注明填写格式**；必须写清用户从首页点击进入的完整中文路径       |
| 6    | **操作(步骤编号123)**  | 按顺序写清：点击什么按钮/链接 → 选择什么下拉项 → 在哪个输入框输入什么内容 → 最后点击哪个提交按钮；**列名必须带括号注明步骤编号要求**；每一步用数字 1/2/3 编号 |
| 7    | **预期(可判定结果)**   | 页面应呈现什么内容、跳转到哪个页面、弹出什么提示、在哪个位置应显示目标结果；**列名必须带括号注明可判定要求**；必须是可观察、可判定的结果，不得模糊               |
| 8    | **实际结果**           | 验收时由执行人填写：通过 / 不通过 / 不涉及；**模板初始时留空**                                                                                                   |
| 9    | **验收人**             | 验收时由执行人填写姓名或账号；**模板初始时留空**                                                                                                                 |
| 10   | **备注**               | 填写账号、前置数据、截图位置、补充说明等；**模板初始可留空**                                                                                                     |

- 表格 Markdown 表头行必须严格为：
  `| 用例编号 | 来源变更编号 | 覆盖类型 | 优先级(P0/P1/P2) | 页面(中文路径+URL) | 操作(步骤编号123) | 预期(可判定结果) | 实际结果 | 验收人 | 备注 |`
