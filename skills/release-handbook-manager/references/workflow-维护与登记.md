# 维护阶段动作与操作判断原则

> 来源：SKILL.md 原 §7.2（维护阶段）+ §八（§8.1/§8.2/§8.3 操作判断原则）
> 加载时机：日常登记一条变更、判断当前该初始化 / 维护 / 巡检

---

### 7.2 维护阶段

1. 读取当前版本号
   - **强制约束**：仅读取，不得在本阶段自动修改 `version` 字段
   - 如发现版本号为占位值（如 `vX.Y.Z` 或空字符串），立即向用户提示："版本号尚未人工维护，请先给出明确版本号后再继续维护发布材料"
2. **版本目录一致性校验（强制新增）**：读取 `release/version.json` 后必须立即执行以下四段判断，**未执行判断不得直接进入任何文件写入操作**：
   - 令 `currentVer = version.version`、`prevVer = version.previousVersion`
   - 检查当前版本目录是否存在：`release/versions/{currentVer}/`
   - 检查上一版本目录是否存在：`release/versions/{prevVer}/`
   - **分支 A（两端都存在）**：`currentVer` 目录存在 且 `prevVer` 目录存在 → 按原流程继续第 3 步
   - **分支 B（当前目录不存在，但上一版存在 —— 典型场景：人工改完 version.json 从 v1.1→v1.2）**：`currentVer` 目录不存在，且 `prevVer` 目录存在 → **必须中断当前流程，强制先进入 `switch-版本切换子流程.md` §7.2.1 版本切换初始化子流程**，完成目录创建 + 模板迁移 + 账号迁移 + 台账迁移后，再从第 3 步继续
   - **分支 C（两端都不存在）**：`currentVer` 目录不存在 且 `prevVer` 目录也不存在 → 立即退回 `init-初始化流程.md` 初始化阶段，按初始化规则从 0 搭建版本目录结构与模板，不得越过初始化直接维护
   - **分支 D（当前目录存在，上一版不存在 —— 典型场景：首个发布版本，`previousVersion` 为空、占位值或其目录尚未创建）**：`currentVer` 目录存在，且 `prevVer` 目录不存在（含 `previousVersion` 字段为空字符串 / `null` / 占位值 `vX.Y.Z` 的情形）→ **视为首版场景，按原流程继续第 3 步**；严禁触发 §7.2.1 版本切换子流程，也严禁因找不到上一版而中止流程或凭空补建上一版目录；涉及「上一版迁移」的动作（模板迁移 / 05-1 账号迁移 / 台账迁移）在本分支下一律跳过，直接采用模板默认值
3. 判断本次需求是否涉及：
   - 数据库结构变更
   - 历史数据修复/回填
   - 菜单权限配置
   - 角色权限配置
   - 字典/参数/流程/模板配置
   - 已有配置文件调整
   - 生产环境配置调整
   - 其他人工操作
4. 根据类型决定：
   - 必须脚本化
   - 允许人工操作
5. 追加或创建对应脚本与更新手册内容
   - **归并优先（强制决策顺序）**：新增 02/03 脚本前必须先按 `scripts-sql-规范.md` §4.3 扫描当前版本已有脚本，同功能单元且满足合并条件的一律追加片段到已有文件，不得直接新建；只有不满足合并条件时才按最大号 +1 新建
   - **文件名即执行序（§4.4 硬保证）**：文件名必须符合 `前缀-NNN(三位定宽)-简述.sql`，同前缀 NNN 唯一，默认追加最大号 +1；跨文件前置依赖除头部人读说明外必须写 `-- @depends` 机器声明，且被依赖脚本序号严格更小；需要插到两个既有脚本之间时按 §4.4.2 从大号到小号整体重编号（文件、@depends、01 表、04 命令同步改），完成后跑 `run-release.ps1 -ListOnly` 确认 0 违例
   - **单一通道（§4.5 一票否决）**：版本目录只放生产发布必执行脚本——测试库专用/造数/基线恢复脚本写入 rta 的 `scripts/test-auto/`，不得放进版本目录；备份等运维动作按 §4.2 登记人工操作，禁止放 SQL 再跳过；每个脚本必须有尾部校验区保证执行有 PASS/FAIL 反馈，不得产生 skip 类脚本
   - 所有内容均归属到已读取的当前版本号下，不得因内容增加而擅自切换或升级版本号
   - **强制约束（与 `switch-版本切换子流程.md` §7.2.1 联动）**：在创建任何文件或写入内容前，必须再次核对「当前操作的目录名 == `release/version.json.version`」，如果仍未创建对应版本目录或仍然写在上一版目录内，**必须立即中止并触发 §7.2.1 先建目录**；严禁「先把 v1.2 的变更写在 v1.1 目录里之后再迁」的跨版本混写行为
   - 如创建或补写 `02-db-xxx.sql` / `03-config-xxx.sql`，必须先在文件头部补齐 §4.1 规定的固定说明区，尤其是 `【预期结果】` 与 `【执行后快速核对】`，不得省略
   - SQL 文件写完后，必须在文件尾部补齐 `-- 【执行后校验SQL】` 固定区；当脚本包含多段逻辑时，校验 SQL 也必须按逻辑分段编号，保证执行人不依赖肉眼翻日志即可判断结果
   - 若 SQL 文件包含多个执行片段，必须为每个片段就近补一段校验写入逻辑，并在尾部输出"全部片段明细 + success_count + fail_count + 失败片段清单"；不得只保留总计数而缺失失败明细
6. 同步补充发布检查清单、发布后验证记录（技术版 05）、功能验收用例（非技术版 05-1）、版本更新日志所需内容
   - **05/05-1 双轨必须同时生成**：不得单独只生成 05 或只生成 05-1，任一缺失即视为维护步骤未完成
   - **05-1 的生成口径**：必须严格按 `templates-05-1-功能验收用例.md` §6.3.1 规范，从 01 §3.1/§3.3 提取用户可感知功能、从 01 §3.4 提取缺陷修复转回归用例、排除 §6.3.1 明确禁止的所有技术术语
   - **05-1 角色准备区账号迁移（强制，分支 D 首版场景下本条整体跳过）**：生成 05-1 时，必须先读取 `previousVersion`，仅检查上一个版本同名 `05-1` 文件中的 `## 2. 角色准备`；若存在同名角色的 `测试账号/测试密码`，则优先迁移到当前版本，找不到时再回落模板默认值；严禁继续追溯更早历史版本
   - **05-1 用例编号反写交叉索引（强制）**：同步生成 05-1 时，若用户在 `01-更新手册.md §3.4 缺陷修复` 中写了 N 条缺陷修复记录（N≥1），则**必须**：
     1. 为每条用户可感知的缺陷修复在 05-1 中生成对应的回归验收用例，并分配唯一 05-1 用例编号（如 `BUG-001`、`ORG-FIX-003` 等）
     2. 将生成的「05-1 用例编号」**反写到 01 §3.4 对应缺陷修复条目的每行末尾**，形成双向交叉索引；格式示例：
        - 01 §3.4 行原内容末尾追加：` 【05-1回归用例：BUG-007】`
        - 05-1 用例的「用例编号」列填写：`BUG-007`，并在「操作/预期」列对应描述该缺陷修复前的原始触发场景与修复后预期结果
     3. 01 §3.4 中纯后台、用户不可感知的缺陷修复（如纯 SQL 性能优化、死锁修复、缓存命中率优化等）不需要进入 05-1，但也必须在行末标注：` 【纯后台修复·不进入05-1】` 以便巡检时区分
   - 如维护过程中判断本次改动可能需要切分版本或升级版本号，必须向用户明确提示建议，等待人工明确指令后再执行版本号变更操作

## 八、操作判断原则

### 8.1 何时应直接初始化

以下情况优先执行初始化：

- 项目内还没有 `release/version.json`
- 项目内还没有版本发布相关规则文件
- 用户明确要求建立版本发布治理机制
- 用户明确要求创建版本更新手册体系

### 8.2 何时应进入维护模式

以下情况优先进入维护模式：

- 项目中已存在版本配置文件与版本目录
- 用户要求补登记当前版本的变更事项
- 用户要求为当前改动补 SQL 脚本、发布清单、更新日志
- （新增）`release/version.json.version` 已被人工维护为新版本号，但 `release/versions/{currentVer}/` 目录尚未初始化（会自动命中 §7.2.1 版本切换初始化子流程）
- （新增）用户发出"切版本 / 开始新版本 / 从上一版材料迁移开新版"等版本切换话术（会自动命中 §7.2.2 触发入口）

### 8.3 何时应进入巡检模式

以下情况优先进入巡检模式：

- 用户要求准备发版
- 用户要求检查某个版本材料是否完整
- 用户要求核对当前版本是否缺少脚本、手册或验证记录
