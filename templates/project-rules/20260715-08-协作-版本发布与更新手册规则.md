# 版本发布与更新手册规则

## 1. 版本号唯一真源规则

- 项目必须维护一个唯一的版本配置文件，当前版本号以该配置文件为唯一真源。
- 版本号格式统一为：`v主版本.次版本.修订号`。
- 禁止以 Git 提交记录、分支名、Tag 名等作为版本号唯一依据。
- 每次进入新的开发迭代或发布周期前，必须先维护版本配置文件中的版本号。
- 当前版本涉及的更新手册、脚本、发布清单、验证记录、更新日志，均必须归属于该版本号。

## 2. 版本材料目录规则

- 版本配置文件路径统一为：`release/version.json`。
- 每个版本的发布材料统一存放于：`release/versions/{版本号}/`。
- 当前版本目录下文件采用单层平铺结构，禁止额外增加多级子目录，避免发布执行时误操作。
- 推荐目录结构如下：

```text
release/
  version.json
  versions/
    v1.0.0/
      01-更新手册.md
      02-db-001-数据库结构变更.sql
      02-db-002-历史数据修复.sql
      03-config-001-菜单权限配置.sql
      03-config-002-角色权限配置.sql
      04-发布检查清单.md
      05-发布后验证记录.md
      05-1-功能验收用例(非技术版).md
      06-版本更新日志.md
```

## 3. 更新手册唯一真源规则

- 每个版本必须对应一份唯一的 `01-更新手册.md`，作为该版本发布内容的唯一真源。
- 开发过程中与当前版本相关的变更事项，必须持续登记到该版本更新手册中。
- 禁止仅在聊天记录、口头沟通、临时文档中保存发布关键信息而不回收至更新手册。

## 4. 强制登记范围规则

- 凡是超出纯代码提交范围、需要额外执行、额外配置、额外迁移、额外说明的内容，都必须登记到当前版本更新手册。
- 强制登记范围至少包括：
  - 数据库表结构变更
  - 字段新增、修改、删除
  - 主键、外键、索引、约束调整
  - 存储过程、触发器等数据库对象变更
  - 历史数据修复、回填、迁移
  - 菜单、权限、角色权限等数据库驱动配置
  - 字典、参数、流程、模板等数据库驱动配置
  - 原有配置文件调整
  - 生产环境配置调整
  - 需要人工执行的发布操作
  - 回滚步骤与回滚前置条件
  - 本版本全部功能变更、缺陷修复与兼容处理说明

## 5. 必须脚本化规则

- 凡是本质上可以通过数据库执行完成的变更，必须提供可执行 SQL 脚本，不允许只写文字说明。
- 以下场景必须脚本化：
  - 数据库表结构变更
  - 字段、主键、外键、索引、约束调整
  - 存储过程、触发器等数据库对象变更
  - 历史数据修复、回填、迁移
  - 菜单配置
  - 菜单下权限配置
  - 角色权限分配
  - 其他可通过数据库增删改查直接完成的系统配置
- 菜单、权限、角色权限等虽然可在页面上人工配置，但因其底层属于数据库可执行操作，必须按脚本化处理，不得归类为人工操作。
- 数据库类脚本文件统一使用 `02-db-xxx-说明.sql` 命名。
- 配置类脚本文件统一使用 `03-config-xxx-说明.sql` 命名。
- 脚本文件必须通过文件名前缀体现类型和执行顺序。
- 每个 `02-db-xxx.sql` / `03-config-xxx.sql` 文件都必须在**文件头部**设置统一固定说明区，至少包含：
  - `【脚本用途】`
  - `【执行前置条件】`
  - `【预期结果】`
  - `【执行后快速核对】`
- `【预期结果】` 必须集中写在文件头部固定区域，禁止零散写在 SQL 中部、尾部或多段注释中，避免执行完成后人工翻找遗漏。
- `【执行后快速核对】` 必须至少提供 1 条可直接复制执行的核对 SQL 或核对步骤，便于执行后快速比对。
- 每个 SQL 文件在**文件尾部**还必须追加独立固定区：`-- 【执行后校验SQL】`。该区域必须提供可直接执行的校验 SQL，尽量返回明确数值、状态或差异计数，禁止仅依赖执行日志中的 `Query OK`、影响行数提示或肉眼逐段翻看日志判断成功与否。
- 当脚本内容较多、步骤较多或包含多段 DDL/DML 时，`-- 【执行后校验SQL】` 必须按脚本内逻辑分段编号，例如：
  - `-- 1. 校验字段是否存在`
  - `-- 2. 校验回填数量是否正确`
  - `-- 3. 校验脏数据是否清零`
- 校验 SQL 应优先使用 `COUNT(*)`、`SUM(...)`、`CASE WHEN ... THEN 'PASS' ELSE 'FAIL' END`、差异集查询等可判定写法，确保执行人直接看结果值即可判断是否通过。
- 对于**一个 SQL 文件包含多个执行片段**的场景，必须采用“**分片段校验 + 汇总结果**”模式：每个片段执行完成后立即执行对应校验 SQL，并把结果写入统一结果集；文件尾部统一输出成功计数、失败计数、失败片段明细。
- 多片段脚本不得只在文件尾部放一个笼统总查询，也不得只统计成功条数而不保留失败明细；至少必须同时输出：
  - 全量片段校验结果明细
  - `success_count`
  - `fail_count`
  - 失败片段清单
- 如数据库支持临时表，优先使用临时结果表（例如 `tmp_rhm_check_result`）收集每个片段的校验结果；如不支持临时表，也必须采用等价的可查询结果集方案，保证最终仍能输出“明细 + 汇总 + 失败项”。

推荐脚本头部模板：

```sql
/*
【脚本用途】
1. {本脚本解决什么问题}

【执行前置条件】
1. {执行前必须满足的条件}

【预期结果】
1. {执行成功后应看到的结果}
2. {需要重点核对的结果}

【执行后快速核对】
1. {核对SQL或核对步骤}
*/
```

推荐尾部模板：

```sql
-- 【执行后校验SQL】
-- 1. {校验项名称}
SELECT CASE WHEN COUNT(*) = 1 THEN 'PASS' ELSE 'FAIL' END AS check_result
FROM information_schema.COLUMNS
WHERE TABLE_SCHEMA = DATABASE()
  AND TABLE_NAME = '{表名}'
  AND COLUMN_NAME = '{字段名}';

-- 2. {校验项名称}
SELECT COUNT(*) AS abnormal_count
FROM {表名}
WHERE {应当不存在的数据条件};
```

多片段脚本推荐模板：

```sql
DROP TEMPORARY TABLE IF EXISTS tmp_rhm_check_result;
CREATE TEMPORARY TABLE tmp_rhm_check_result (
    id INT PRIMARY KEY AUTO_INCREMENT,
    check_name VARCHAR(200) NOT NULL,
    expected_desc VARCHAR(500) NOT NULL,
    actual_desc VARCHAR(500) NOT NULL,
    pass_flag TINYINT NOT NULL,
    check_time DATETIME NOT NULL DEFAULT CURRENT_TIMESTAMP
);

-- 片段1：执行 SQL
-- {片段1执行语句}

-- 片段1：执行后校验并写入结果
INSERT INTO tmp_rhm_check_result (check_name, expected_desc, actual_desc, pass_flag)
SELECT
    '片段1-{校验项名称}',
    '{预期结果说明}',
    CONCAT('{实际结果前缀}=', COUNT(*)),
    CASE WHEN {通过条件} THEN 1 ELSE 0 END;

-- 片段2：执行 SQL
-- {片段2执行语句}

-- 片段2：执行后校验并写入结果
INSERT INTO tmp_rhm_check_result (check_name, expected_desc, actual_desc, pass_flag)
SELECT
    '片段2-{校验项名称}',
    '{预期结果说明}',
    CONCAT('{实际结果前缀}=', COUNT(*)),
    CASE WHEN {通过条件} THEN 1 ELSE 0 END;

-- 【执行后校验SQL】
-- 1. 查看全部片段校验结果
SELECT
    id,
    check_name,
    expected_desc,
    actual_desc,
    CASE WHEN pass_flag = 1 THEN 'PASS' ELSE 'FAIL' END AS check_result,
    check_time
FROM tmp_rhm_check_result
ORDER BY id;

-- 2. 查看汇总结果
SELECT
    COUNT(*) AS total_count,
    SUM(CASE WHEN pass_flag = 1 THEN 1 ELSE 0 END) AS success_count,
    SUM(CASE WHEN pass_flag = 0 THEN 1 ELSE 0 END) AS fail_count
FROM tmp_rhm_check_result;

-- 3. 仅查看失败片段
SELECT
    id,
    check_name,
    expected_desc,
    actual_desc
FROM tmp_rhm_check_result
WHERE pass_flag = 0
ORDER BY id;
```

## 6. 允许人工操作规则

- 仅以下场景允许保留为人工操作步骤：
  - 修改已有配置文件的内容调整（不含新增配置文件）
  - 生产环境配置类操作
  - 确实无法脚本化的事项
- 凡属于人工操作的事项，必须在版本更新手册中明确写清：
  - 操作入口
  - 操作顺序
  - 操作内容
  - 目标结果
  - 校验方式
- 禁止以“现场处理”“按实际情况调整”等模糊语句替代明确操作步骤。

## 7. 发布执行规则

- 每次版本发布时，必须严格按照该版本更新手册执行。
- 发布执行顺序必须明确区分：
  - 发布前检查
  - 数据库脚本执行
  - 配置脚本执行
  - 应用部署
  - 人工操作执行
  - 发布后验证
  - 回滚处理
- 禁止凭记忆、聊天记录或临时口头说明直接上线。

## 8. 更新日志沉淀规则

- 更新手册不仅用于发布执行，还必须记录当前版本全部变更事项。
- 正式发布时，对内发布说明、对外更新日志、升级说明等内容，必须优先从当前版本更新手册提炼生成。
- 禁止在发布时重新临时回忆和拼凑版本变更内容。

## 9. 发布材料完整性规则

- 每个版本的发布交付必须同时包含：
  - `01-更新手册.md`
  - `02-db-xxx.sql`
  - `03-config-xxx.sql`
  - `04-发布检查清单.md`
  - `05-发布后验证记录.md`（面向测试/开发人员的技术版验证）
  - `05-1-功能验收用例(非技术版).md`（面向产品经理/最终用户/UAT 的非技术版验收，采用页面/操作/预期三段式）
  - `06-版本更新日志.md`
- 如某类脚本不涉及，可在更新手册中明确标记"不涉及"。
- 仅有文档、没有可执行脚本，不视为完整交付。
- 仅有脚本、没有手册说明，不视为完整交付。
- `05` 与 `05-1` 为双轨配套，两者缺一不可：技术验证由 `05` 承载，用户验收由 `05-1` 承载，不得互相替代或省略。
- 生成 `05-1-功能验收用例(非技术版).md` 的 `## 2. 角色准备` 时，必须优先读取 `release/version.json` 中的 `previousVersion`，并仅检查上一个版本同名文件中的账号信息。
- 若上一个版本同名 `05-1` 文件存在，且 `角色准备` 表格中已有 `测试账号` / `测试密码`，则应按 `角色` 列同名匹配优先迁移到当前版本。
- 迁移时仅允许复用 `测试账号`、`测试密码` 两列；不得迁移 `是否已准备`、`备注`、历史勾选状态等执行态信息。
- 若上一个版本未填写密码或密码为空，则当前版本默认仍按 `111111` 处理。
- 若 `previousVersion` 为空、上一个版本文件不存在、无角色准备区或无同名角色，则当前版本按模板默认值生成即可。
- 禁止为了补账号信息继续追溯更早历史版本；只允许检查上一个版本，不得扫描更早版本。

## 10. 维护责任规则

- 当前版本的需求开发人员，在涉及上述范围的改动时，必须同步维护更新手册与脚本。
- 版本发布负责人在发版前，必须核对版本号、更新手册、脚本、验证项是否一致。
- 如存在未登记事项，不得视为当前版本发布材料已完成。
