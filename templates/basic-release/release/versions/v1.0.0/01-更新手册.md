### 4.2 四种执行场景（一句话即可，不贴命令模板）
按目标库选择范围，顺序执行，失败立即 STOP：
- 全新空库：按编号全跑
- 已含基础结构老库（默认）：跳过基础结构段，从后续段开始
- 只跑某个批次段：仅跑对应编号范围
- 只跑某个改造模块（依赖前置模块已跑过）：仅跑对应编号范围

> 每条脚本的成功验证：优先看脚本尾部 `-- 【执行后校验SQL】` 返回的 PASS/FAIL、success_count、fail_count 与失败片段清单；不得仅以 `Query OK` 或肉眼翻日志为通过依据。

## 6. 发布执行步骤（按顺序，禁止混包跳步）

### 6.1 发布前检查（全部通过方可开始）
1. 只认 `release/versions/{版本号}/` 为唯一操作入口（不得提前创建下一版目录）
2. `04-发布检查清单.md` 所有章节全部打勾
3. 所有门禁（grep / 关键字 / 开关初始值）全部命中预期
4. 所有真实时间窗口 / 压测 / 签字栏（§9）已齐全
5. 数据库完整备份 0.5h 内最新一份存在

### 6.2 执行顺序
1. **发布前检查**：按 04 所有章节逐行打勾
2. **SQL 脚本**：按 §4.2 执行场景跑对应 02-db-xxx 编号范围（失败立即 STOP）
3. **配置脚本**：按 03-config-xxx 编号顺序执行（只读校验脚本按需执行）
4. **人工流程配置**：后台流程管理/字典管理等必须人工导入或维护的内容
5. **应用部署**：先后端 → 再前端 → 预热 → 冒烟
6. **冒烟测试**：技术按 `05-发布后验证记录.md`；业务按 `05-1-功能验收用例(非技术版).md` 勾验
7. **稳定观察**：启动观察窗口（如有多阶段灰度则按介入点执行）
8. **验证归档 + 签字**：05 / 05-1 结果齐全 → 三方签字 → 同步更新 06 版本更新日志

## 7. 回滚方案（仅限紧急场景，一张简表）

| 范围 | 是否允许 | 简要步骤 |
| :-- | :-- | :-- |

| 数据库数据清理脚本（永久删除类） | ❌ 不提供回滚 | 幂等 DROP IF EXISTS 误执行无副作用 |
| 应用版本回退 | ✅ 有前一版部署包前提下 | 切回前一版包 + 清相关缓存 |
| 超出以上范围的严重事故 | ❌ 不提供自动回滚路径 | 走专项事故修复方案，不得尝试未经验证的快速脚本 |
