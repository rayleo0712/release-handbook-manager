# 快速开始

本文用于帮助你把 `release-handbook-manager` 快速接入到一个现有项目中。

在 AI 协同开发场景中，这个 Skill 主要用于解决下面 5 类问题：

1. 减少每次整理版本发布资料、发布步骤和功能说明的重复劳动
2. 在开发过程中自动沉淀当前版本的变更记录
3. 自动生成发布所需的 SQL 和其他脚本
4. 自动生成发版时的更新步骤
5. 自动生成最终版本更新日志

如果你的团队在发版前还经常临时补资料、补 SQL、补操作步骤、补更新说明，那么这份文档就是最适合的接入入口。

> 重点说明：
> 本 Skill 以“AI 深度参与开发过程”为主要适用前提。
> 如果项目基本不用 AI 开发，或只在临近发版时少量使用 AI，不适合使用本 Skill。

## 1. 放置 Skill 文件

将仓库中的技能文件复制到目标项目的 Skill 目录：

```text
.trae/skills/release-handbook-manager/SKILL.md
```

如果你的 AI 协作平台使用的不是 `.trae/skills/` 结构，也可以放到该平台约定的 Skill 目录，只要平台能够识别 `SKILL.md` 即可。

## 2. 初始化项目发布治理

在聊天中直接发出以下指令：

```text
请用 rhm 初始化当前项目的版本发布治理，版本号先设为 v1.0.0
```

> **一票否决红线提示**：
> 初始化 `release/version.json` 时，`version` 字段必须由人工明确指令给出具体版本号（如上面的 `v1.0.0`）。
> 如果没有人工明确给出版本号，AI 只能写入占位值（如 `vX.Y.Z`）并明确提示人工维护，严禁擅自填入猜测版本号。
> 后续维护阶段，AI 不得在任何场景下自动 bump、自动升级或自动改版本号。

初始化完成后，项目内通常会出现以下结构（完整版本目录文件号固定为 7 份：01 → 02 → 03 → 04 → 05 → 05-1 → 06，其中 02/03 在无对应变更时可暂不创建实体文件，但文件号口径保持 7 份不变）：

```text
release/
  version.json
  versions/
    v1.0.0/
      01-更新手册.md
      04-发布检查清单.md
      05-发布后验证记录.md
      05-1-功能验收用例(非技术版).md
      06-版本更新日志.md
```

如果当前版本暂时没有数据库或配置类变更，`02-db-xxx.sql` 与 `03-config-xxx.sql` 不必在初始化时强行创建。

## 3. 理解主版本真源

项目默认采用“全项目单一总版本号”模式。

- 主版本号统一维护在 `release/version.json`
- `frontend`、`backend`、`client`、`uniapp` 等目录不再单独维护主版本真源
- 某个模块如果需要单独记录版本，只能作为附属信息补充，而不能取代总版本号

## 4. 开发过程中如何维护

当你完成一个需求后，可以继续在聊天中使用类似指令：

```text
用 rhm 维护当前版本变更
```

```text
用 rhm 为这次需求补发布材料
```

在这个阶段，Skill 会重点处理：

- 把开发过程中的变更持续登记进 `01-更新手册.md`
- 对可脚本化内容自动生成或补齐 SQL / 脚本
- 把发版需要的步骤整理进版本材料
- 补充发布检查清单和发布后验证材料
- 为后续版本更新日志提前沉淀来源内容

日常维护常用指令示例：

```text
用 rhm 将本版 05-1 切换为输出模式 B 对外交付版
```

```text
用 rhm 执行 05-1 P0/P1/P2 PowerShell 计数并回填 §八汇总表
```

## 5. 发版前如何巡检

在准备发版时，可以直接使用：

```text
用 rhm 检查 v1.0.0 是否可以发版
```

此时会重点检查：

- 版本号与目录是否一致
- 数据库脚本和配置脚本是否齐全
- 人工操作项是否明确
- 回滚方案和发布后验证项是否完整

## 6. 什么时候必须补 SQL

以下内容不允许只写说明，必须补 SQL：

- 表结构变更
- 字段、主键、外键、索引、约束调整
- 历史数据修复、回填、迁移
- 菜单、权限、角色权限配置
- 其他数据库驱动配置

核心原则是：

- 最大化避免人工操作页面更新数据
- 菜单、权限、角色授权等配置，不应在发版后再通过后台页面做繁琐人工更新
- 只要底层本质是数据库可执行操作，就优先生成 SQL 或其他可执行脚本
- **[新增] 每个 SQL 脚本必须头部含四字段（用途/前置条件/预期结果/快速核对） + 尾部含独立【执行后校验SQL】区（使用 PASS/FAIL/COUNT 等可判定写法）**
- **[新增] 多片段 SQL 脚本必须采用「分片段校验 + 汇总结果」模式，最终输出明细 + success_count + fail_count + 失败清单，禁止只放一个笼统总查询**

## 7. 什么时候允许人工操作

仅以下情况允许保留为人工步骤：

- 修改已有配置文件
- 生产环境配置
- 确实无法脚本化的事项

即使允许人工操作，也必须在手册中明确记录操作入口、顺序、内容、目标结果和校验方式。

## 8. 推荐接入顺序

推荐按以下顺序接入：

1. 先初始化治理结构
2. 再把一个真实需求用 `rhm` 补录一次
3. 再在一次真实发版前用 `rhm` 做巡检

这样团队最容易直接感受到它的价值：

- 平时少做一轮人工整理
- 发版前少补一轮 SQL 和步骤
- 发版时少靠临时沟通和记忆
- 发版后能直接拿到版本更新日志基础材料

## 9. 配套自动化测试 Skill（release-test-auto / 简称 rta）

完成初始化和发布材料维护后，可配套使用同仓库新增的 `release-test-auto`（简称 `rta`）Skill，把 05-1 验收用例从「人工点击」升级为「IDE 终端可独立运行的自动化测试」。

### rta 解决什么问题

- 基于当前版本的 05-1 真源 + 账号准备 + 版本真源，自动生成启动脚本、数据库恢复脚本、测试执行脚本
- 在 IDE 内置终端或等价命令行环境独立运行，不依赖聊天会话持续在线
- 支持断点续跑（每条用例结果立即落盘，会话中断后可从断点继续）
- 支持正反向双覆盖：05-1 正向用例 + AI 自动补充权限/状态/输入三类逆向用例（需辅助真源充足）
- 支持修复 bug 后重启服务续跑，支持按需恢复数据库基线
- 最终结果回填 05/05-1，并产出 `test-output/final-report.md` 结构化报告

### rta 常用触发语句

```text
请基于当前 05-1 自动跑一轮 UAT
```

```text
恢复测试基线后执行回归测试
```

```text
让 AI 模拟人工测试当前版本
```

```text
修完 bug 后重启并续跑自动化测试
```

```text
生成数据库恢复、校验和自动化测试脚本
```
