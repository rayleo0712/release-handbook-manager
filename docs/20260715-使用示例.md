# 使用示例

本文整理 `release-handbook-manager` 在真实协作中的常见使用方式，便于快速复制到聊天中触发。

这些示例主要围绕 5 个目标展开：

1. 少做一轮版本发布资料整理
2. 自动记录开发过程中的变更
3. 自动生成 SQL 和其他发布脚本
4. 自动生成发版执行步骤
5. 自动生成版本更新日志

## 1. 初始化项目

```text
请用 rhm 初始化当前项目的版本发布治理，版本号先设为 v1.0.0
```

适用场景：

- 项目里还没有 `release/version.json`
- 项目里还没有版本发布规则
- 团队准备第一次把发版流程收口到标准目录中

## 2. 维护当前版本变更

```text
用 rhm 维护当前版本变更，这次需求涉及 backend 接口调整、frontend 页面改动，以及一条历史数据回填 SQL
```

适用场景：

- 某次需求已经开始落代码
- 需要把数据库脚本和变更说明补到当前版本中
- 不希望把发布信息继续散落在聊天记录里
- 希望开发过程中自动沉淀版本变更记录

## 3. 补脚本化产物

```text
用 rhm 为这次需求补发布材料，这次涉及菜单新增、权限点新增、给角色补权限，请同时生成可执行 SQL
```

适用场景：

- 菜单、权限、角色权限等数据库驱动配置需要标准化
- 希望最大化避免发版后再人工操作后台页面更新数据
- 不能接受菜单、权限、角色授权等配置在上线后仍靠繁琐人工更新

## 4. 处理人工操作事项

```text
用 rhm 维护当前版本变更，这次不涉及数据库，但涉及生产环境参数调整和已有配置文件修改，请补到更新手册里
```

适用场景：

- 变更不能完全脚本化
- 但仍然需要把发布步骤写成可以执行和验收的材料
- 希望自动整理出发版时的更新步骤，而不是临时口头安排

## 5. 发布前巡检

```text
用 rhm 检查 v1.0.0 是否可以发版
```

适用场景：

- 准备上线
- 需要确认脚本、手册、验证、回滚材料是否完整
- 希望在发版前直接拿到结构化的更新步骤和检查结果

## 6. 多模块仓库场景

```text
用 rhm 维护当前版本变更，这次涉及 backend、frontend、client 三个目录，但仍然统一归档到 v1.0.0
```

适用场景：

- 仓库中存在多个子目录
- 但整体仍作为一套系统统一发版

说明：

- 默认只维护一个总版本号
- 子模块不是独立主版本真源
- 如需记录模块级版本，只能作为附属信息补充

## 7. 升版本后继续维护

```text
请用 rhm 将当前项目版本切换到 v1.1.0，并初始化 v1.1.0 的发布材料
```

适用场景：

- 准备开始下一轮开发周期
- 需要建立新版本目录并延续同一套治理机制
- 希望下一版本的更新日志来源材料从一开始就持续沉淀

## 8. 推荐表达方式

为了让 Skill 更稳定地进入正确工作模式，推荐在指令中显式写出以下信息：

- 使用 `rhm`
- 当前动作：初始化 / 维护 / 巡检
- 当前版本号
- 涉及模块
- 是否涉及数据库脚本
- 是否涉及人工操作

推荐组合示例：

```text
用 rhm 维护 v1.1.0，这次涉及 backend 和 frontend，包含 1 个表结构变更、2 条菜单权限 SQL，以及 1 项生产环境人工配置
```
