# 设计说明

本文用于说明 `release-handbook-manager` 的设计目标、关键约束和取舍原则，方便在后续独立维护时保持一致口径。

## 1. 设计目标

这个 Skill 的目标不是生成一份漂亮文档，而是把发布阶段最容易失控的工作前移并标准化。

> 重点前提说明：
> 本 Skill 以“AI 深度参与开发过程”为主要适用前提。
> 它最适合 AI 持续参与需求分析、代码实现、改动整理和发布收口的协同开发场景。
> 如果项目基本不用 AI 开发，或只在临近发版时少量使用 AI，不适合使用本 Skill。

它要解决的问题包括：

- 版本号定义不统一
- 非代码变更缺少沉淀位置
- 可脚本化操作没有形成可执行 SQL
- 人工操作描述模糊
- 发布检查、发布后验证、版本日志没有统一来源

因此它本质上是一个“发布治理 Skill”，而不只是“发布文档生成器”。

## 1.1 能力边界

本 Skill 当前并不自带独立的“版本对比分析引擎”或“SQL 自动生成引擎”。

它的优势在于：

- 统一发布治理结构
- 规范版本手册和交付边界
- 在 AI 已掌握较完整开发上下文时，辅助沉淀变更、脚本、步骤和日志

它的限制在于：

- 不能凭空知道未留痕的变更
- 不能在 AI 未深度参与开发过程时，稳定自动判断全部功能变化和所需脚本
- 不能脱离上下文就承诺自动生成完整发布材料

因此，对外介绍时应重点强调：

- 它适合深度使用 AI 开发的团队
- AI 持续参与开发过程时效果最佳
- 在低 AI 参与场景下，不适合使用本 Skill

## 2. 为什么版本号不依赖 Git

本 Skill 刻意不把 Git 作为主版本号真源，原因是：

- 多人协作时，Tag、分支、提交习惯不一定统一
- 某些团队会先开发后补 Tag
- 真实发版节奏不一定和 Git 节点一一对应

因此主版本号统一由：

```text
release/version.json
```

来维护。

Git 可以继续承担代码追踪职责，但不能替代版本配置文件。

### 2.1 版本号必须人工维护（一票否决红线）

这是后续补强的关键约束，原因是：

- AI 在开发过程中经常因代码变更"顺手"改版本号，容易引发版本混乱、目录混乱、发布节奏失控
- 版本号本身是管理决策产物（需要先有人决定"这一版要发什么"，不是纯技术自动计算产物
- 版本号一旦被 AI 随意 bump，版本目录、已沉淀材料会同步错位，修复成本高

因此硬性规定：

- `version` 字段的写操作**只能**由人工明确指令触发
- AI 仅允许两种合法写场景：(1) 人工明确给出具体目标版本号并要求写入；(2) 人工明确指令版本号变更意图
- 初始化时无人工指出版本号，必须用占位值，严禁猜值
- 维护阶段 AI 只能读 version，发现有版本号变更需求时必须提示人工，不得自行写入

## 3. 为什么采用单层平铺结构

版本材料最终采用：

- `01-更新手册.md`
- `02-db-001-xxx.sql`
- `03-config-001-xxx.sql`
- `04-发布检查清单.md`
- `05-发布后验证记录.md`（面向测试/开发的技术版）
- `05-1-功能验收用例(非技术版).md`（非技术版·面向产品经理/UAT/业务用户·8列结构·完整级输出·支持 Output Mode Switch（A 内部评审版 / B 对外交付版）双模式切换；含模块、场景、前置条件、操作步骤、预期结果、优先级P0/P1/P2、实际结果、验收人8列）
- `06-版本更新日志.md`

而没有把 `02`、`03` 拆成多级子目录。

这样做是为了：

- 降低上线操作时进错目录、漏执行的概率
- 让执行顺序直接体现在文件名中
- 让手册引用脚本时更直接

这是一种偏向“发布执行安全性”的设计取舍。

## 4. 为什么强调“必须脚本化”

在实际项目中，最容易被轻描淡写处理的，恰恰是这些内容：

- 菜单配置
- 权限点配置
- 角色授权
- 字典和参数初始化
- 历史数据修复

这些事项在很多团队里常被写成：

- “去后台加一下菜单”
- “给管理员配下权限”
- “发版时顺手改一下数据”

这类交付方式几乎不可追踪、不可复盘、不可复用。

因此本 Skill 明确规定：

- 只要底层本质是数据库操作，就必须优先产出 SQL
- 页面可操作不代表可以归类为人工操作

## 5. 为什么保留人工操作白名单

并不是所有发布动作都适合脚本化。

例如：

- 修改已有配置文件
- 生产环境专属配置
- 运维平台上的特殊动作
- 某些必须人工判断的步骤

这类事项允许保留为人工操作，但要求是：

- 不能模糊
- 不能临场决定
- 不能只靠聊天记录

所以 Skill 会要求把人工步骤也写成“可执行说明”。

## 6. 为什么默认只有一个总版本号

在多目录仓库中，例如：

- `backend`
- `frontend`
- `client`
- `uniapp`

如果每个目录都维护一个主版本号，很容易带来这些问题：

- 一次发布到底看哪个版本号
- 更新手册该归属哪个目录
- 同一轮需求跨前后端时无法统一沉淀

因此默认策略是：

- 整个项目只维护一个总版本号
- 子模块不是独立主版本真源
- 模块版本如果确有需要，只能作为附属信息记录

跨仓库版本治理补充说明：如某子仓库在同一总版本号中只承担纯 SQL / 纯 denorm / 纯双写职责，不对外暴露用户可见功能，则该子仓库的 `05-1-功能验收用例(非技术版).md` 可声明为空，正文写入固定文字：「本子仓库无用户可见功能，05-1非技术验收用例清单为空」，但文件本身必须存在，不可缺省。

## 7. 工作流拆分

本 Skill 把工作流拆成 3 个阶段：

### 7.1 初始化

负责把治理骨架建起来：

- 版本配置文件
- 项目规则文件
- 当前版本目录
- 模板文档

### 7.2 维护

负责把每次需求的发布影响补录进去：

- 变更摘要
- SQL 脚本
- 人工步骤
- 发布检查
- 发布后验证

### 7.3 巡检

负责在发版前做完整性核对：

- 材料是否齐全
- 逻辑是否自洽
- 是否具备可执行与可回滚能力

## 8. 适合独立仓库维护的原因

这个 Skill 很适合后续独立成一个专门维护各类 Skill 的仓库，因为它具备：

- 明确的输入和输出边界
- 可复用的目录结构
- 可扩展的模板机制
- 面向协作流程而不是面向单个业务的规则体系

后续如果要继续扩展，可以考虑新增：

- 多数据库方言模板
- 多语言 README
- GitHub Action 示例
- 发布日志多口径模板
- 子模块附属版本记录模板

## 9. 为什么新增 SQL 可校验机制

实际项目中，SQL 脚本上线后最常见的问题是：

- 执行完没有快速判断是否成功的手段，只能靠肉眼看日志或临时写查询
- 多段 DDL/DML 混在一个文件时，中间某段失败但最后只看到 Query OK，误以为整体成功
- 预期结果写在 SQL 注释中部或尾部，发布时很难快速对照

因此新增强制规则：

- 每个 SQL 脚本头部必须有四个固定字段：【脚本用途】【执行前置条件】【预期结果】【执行后快速核对】
- 每个 SQL 脚本尾部必须有独立 `-- 【执行后校验SQL】` 区，优先用 PASS/FAIL、COUNT、SUM 等可判定写法
- 多片段脚本必须采用"分片段校验 + 汇总结果"模式：临时结果表收集每段校验，最终输出明细 + success_count + fail_count + 失败清单

这样发布执行人员拿到脚本就有明确的"成功判定入口"，不需要靠临场回忆去核对。

## 10. 为什么 05-1 角色账号信息要从上一版本迁移

在多版本连续迭代场景中，测试账号和密码属于稳定复用资源，不应该每个版本重新填写。同时为了避免无限追溯到更早历史版本带来不确定因素，明确迁移边界：

- 读取真源严格按"当前版本优先，上一个版本兜底"规则，不得追溯更早
- 仅允许迁移 `测试账号`、`测试密码` 两列，不得迁移是否已准备、备注、历史勾选等执行态信息
- 这样既保留账号复用价值，又把追溯边界控制在一次发布回溯范围内

## 11. 与配套 Skill `release-test-auto`（rta）的关系

本仓库同时新增了配套 Skill `release-test-auto`（简称 `rta`），两者是真源治理与执行落地的分工关系：

| Skill | 职责 | 边界 |
|---|---|---|
| `rhm` (release-handbook-manager) | 发布材料真源治理 | 负责版本号、更新手册、SQL/配置脚本、04清单、05/05-1 真源、06日志的生成与维护 |
| `rta` (release-test-auto) | 自动化测试执行落地 | 负责读取 rhm 产出的 05-1、账号准备、版本真源，自动生成启动脚本、数据库恢复脚本、测试执行脚本，在 IDE 终端独立运行、断点续跑、产出结果并回填到 05/05-1 |

两者不能互相替代：

- 没有 rhm，rta 缺少真源输入，无法知道测什么、用什么账号测、基于什么版本测
- 没有 rta，rhm 产出的验收用例只能靠人工点击执行，无法沉淀可恢复自动化结果

新增 rta 后，整个仓库形成「真源 → 执行 → 回填归档」的完整闭环。
